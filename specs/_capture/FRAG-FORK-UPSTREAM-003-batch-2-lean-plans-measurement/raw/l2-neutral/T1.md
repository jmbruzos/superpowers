# La ficha que pierde un miembro se recalcula — neutral summary

## Scope

Covers the ForceRule move in `PersistenceStepHandler.persistMembership`, where an active golden record loses a member and today only cleans keys, `source_count` and cache. Moves after absorption, consolidation, manual merge, and spans toward missing, deleted or orphaned records are excluded, since the losing record is not active. Review-queue resolution does not touch membership. Unmerge keeps its behaviour and gets a lineage regression test. The survivorship chain private to `StewardshipService` moves to a shared component, behaviour-preserving, so one owner holds the calculation. A record that survived a manual merge is handled with a targeted recalculation rather than a full one.

## Recomputation mechanism

A new port method, `SourceRecordVersionReader.findVersionsOfMembers`, returns all Silver versions of given members as a new `MemberVersion` record, in the existing query's deterministic order. `MemberSurvivorshipRecomputer` offers a static `chain` — the moved create-then-update loop, `null` for no versions — and `recompute`, which reads current members, their versions and the active schema's survivorship config, chains with the injected `MergeEngine` (whose override provider keeps applying value overrides and pins), and resolves score and freshness. It returns a sealed `Outcome`: `NoMembers`, `NoResolvableVersions`, or `Recomputed`. `StewardshipService` maps its entities to `MemberVersion` and delegates, including a second loop in `reSurvivorshipFromSourcesWithOverride`. A new `LosingMemberHandler.apply` applies the rule on the locked record when its status is null or active. For an ordinary record, `Recomputed` rewrites data, lineage, score, freshness and audit fields with `saveAndFlush`. For a manual-merge survivor, only fields whose current lineage names the departed record, or that a just-deactivated pin of it fixed, take the recomputed value and lineage, or are removed if absent; other fields stay. `NoResolvableVersions` leaves the record untouched, logs a warning and increments a skip counter; the move proceeds. The spec places this logic in a private `recomputeAfterLosingMember` step inside `PersistenceStepHandler`; the plan puts it in the separate, optional `LosingMemberHandler` collaborator.

## Field lineage and `previous`

After recalculation no lineage entry's `source_record_id` may name the departed record outside `previous`, which counts as history. Rebuilding `previous` against persisted values is not addressed.

## Losing the last member

`NoMembers` sets status `orphaned`, empties `golden_data` and `field_lineage`, nulls `latest_source_received_at`, and keeps `quality_score`; an info log and a counter are recorded. The departed record's history stays in the closed span. Zero `source_count` and no blocking keys already hold today and are regression-checked. A manual-merge survivor losing its only member becomes orphaned with its rule still active.

## Pins/overrides/ForceRules on the departed record

Before recalculation, active source pins on the losing record that pin the departed identity — full identity, or id alone for a legacy pin with no recorded source, same predicate as `autoDeactivatePins` — are deactivated with reason `auto_member_left`, actor `system:pipeline`, and a deactivation timestamp. Another source's pin with the same id stays active. Value overrides keep applying. The manual merge's `GOLDEN_TO_GOLDEN` ForceRule is untouched, and `/admin/re-survivorship` keeps answering 409 for that record. An orphaned record stops being a valid ForceRule target, as today.

## Locking/concurrency/retries

The work runs inside the Persistence transaction, on the record locked `FOR UPDATE` before the move, after `cleanUpAfterLosingMember` and before the native-update `refreshSourceCounts`, which a later save would overwrite. Exceptions are not caught: the whole step, move included, rolls back under the single retry and dead-letter policy. A concurrent incremental merge holding the old version fails the expected-version check and goes back to Merge, where it sees the recalculated data.

## Events and cache invalidation

Existing after-commit eviction remains. All events publish only after commit; a rollback publishes nothing and errors are logged. Each deactivated pin emits `FieldOverrideAutoDeactivated`. After a `Recomputed`, if data or score changed, `GoldenRecordUpdated` is emitted through a new emitter overload adding `reason: member_left`, `version`, `fields_changed` and `previous_values`; the existing signature stays. When the record is written (full, targeted, or orphaned), a `PRODUCED` edge from the run with `action: member_left` is added. The step output gains `losing_member_recomputed` with a full/targeted mode, or `losing_member_orphaned`.

## Quality score and tier

`QualityScoreResolver` recomputes the score at `Instant.now()`, as `MergeStepHandler` does; in the targeted case, over the resulting data. Freshness uses only the remaining members' versions. A tier crossing emits `GoldenRecordQualityChanged` and increments the tier-change counter, using the existing guard. Tier handling for the orphaned outcome is not addressed beyond the score staying unchanged.

## Downstream propagation

A project rule says an orphaned record does not propagate downstream, so orphaning emits no `GoldenRecordUpdated`. No event announces orphaning, so downstream consumers are not told; such an event is to be proposed later.

## Tests planned

Unit tests for the adapter and recomputer (three outcomes, version order, empty chain). Handler unit tests: full recomputation; orphaning without the update event; `PRODUCED` edge; no-versions skip with warning and counter; non-active statuses; after-commit-only events; failure publishing nothing, also after pin deactivation; legacy-pin matching; pins before recompute; targeted replacement, including a legacy-pin field. Persistence tests: call before the count refresh, output keys, failure skipping the refresh, other branches not calling it. The spec asks for one in-order check of the full sequence; the plan covers it by combining three tests. Integration tests, with expected values taken from the remaining member's own data: full recomputation, sole-member orphaning, pin deactivation with a value override still applied, targeted survivor, unmerge regression. Existing stewardship tests pass unchanged; 80% coverage on new classes.

## Migrations

Not addressed for the chosen design; the rejected mark-and-sweep alternative was turned down partly because it needed a new migration.

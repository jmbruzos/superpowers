# La ficha que pierde un miembro se recalcula — neutral summary

## Scope

Covers the single-record move branch of `PersistenceStepHandler.persistMembership` (the `membershipRepository.move` call with `kind != null`), which today only cleans keys and source count on the losing record L. The goal is a stated invariant: closing a span and leaving L active recomputes L in the same transaction, or marks it `orphaned` when no members remain. The component is invoked whatever the move kind; it checks L's status itself and does nothing when L is not active (legacy span of an absorbed record, orphan route). It is not invoked after the consolidation's `moveAllMembers`, whose losers are `merged` and unlocked. Unmerge already recomputes and only switches to the shared replay. Manual merge and review-case resolution are out of scope. A manual-merge survivor (target of an active `GOLDEN_TO_GOLDEN` ForceRule) gets a selective recomputation.

## Recomputation mechanism

`MemberSurvivorshipReplayer`, a new class in `mdm-ingest-service`, takes over the `create`/`update` chain from `StewardshipService.reSurvivorshipFromSources(…, MergeEngine)`, which delegates with unchanged signature and callers; `reSurvivorshipFromSourcesWithOverride` is excluded. `LosingMemberRecomputer.apply(LosingMember)` joins the caller's transaction and returns `RECOMPUTED`, `RECOMPUTED_SELECTIVE`, `ORPHANED`, `NOT_ACTIVE` or `UNRESOLVED`. It reads L (null status counts as active), deactivates pins to the departed before the replay, reads current members after the move, loads all their Silver versions in `findVersionsOfMembers` order, and replays them with the Spring `MergeEngine` bean (active value overrides still apply), using the run's `ctx.getSurvivorshipConfig()`; a null config is passed through and the engine falls back to `most_recent`. `golden_data` and `field_lineage` are replaced, never merged. For a manual-merge survivor only fields whose current lineage named the departed take the replay's value and entry (or disappear); the rest is untouched. The bundle notes a project rule excluding manual-merge survivors from re-survivorship conflicts with the rule that the origin record is recomputed. The task also treats a legacy-pin lineage entry (`source = "stewardship"`, departed id) as attributed to the departed, beyond the spec's wording.

## Field lineage and `previous`

No current lineage entry may name the departed identity. A field changed versus the old `golden_data` gets `previous = {value, source of the old entry, changed_at}`; unchanged or new fields get `previous = null`, never the chain's intermediate value. A field supplied only by the departed disappears. Unmerge's lack of `previous` is left open, out of scope.

## Losing the last member

L becomes `orphaned`, following a project rule over a conflicting one that says `absorbed`, since a rule move is not an absorption. `golden_data`, `field_lineage` and `quality_score` are kept unchanged as a read-only historical snapshot; source count goes to zero and keys are removed by the existing paths; pins are deactivated the same way. Rules pointing at it are ignored with a warning.

## Pins/overrides/ForceRules on the departed record

Active `SOURCE_PIN` overrides of L pinned to the departed (same id, and same source if the pin has one) are deactivated with reason `auto_member_moved`, actor `system:pipeline`, and `FieldOverrideAutoDeactivated` after commit with `survivorGoldenRecordId = F`. A pin with the same id but another source is untouched. Value overrides keep applying, including on a field only the departed supplied. ForceRules are only read, to detect a manual-merge survivor; no change to them is addressed.

## Locking/concurrency/retries

L is already locked `FOR UPDATE` by the caller; the task re-reads it with `findByIdForUpdate`. Any failure propagates and rolls back the whole persistence transaction: lock conflicts go back to merge, other errors retry `persistenceMaxRetries` times then go to the dead-letter queue. L is never half-written. The one declared exception is `UNRESOLVED` (members but no Silver versions): the move proceeds, only pins change, with a warning.

## Events and cache invalidation

For a recomputed or orphaned L: the existing `evictAfterCommit(L)` and `golden_record.updated` after commit, which `CacheInvalidationListener` consumes on other pods. On a tier change, `GoldenRecordQualityChanged` with L's own old and new scores. `maybeEmitQualityTierChange` is not reused because it compares against F and publishes inside the transaction. All events are `afterCommit`; nothing publishes on rollback.

## Quality score and tier

`quality_score` is recomputed by `QualityScoreResolver` at `Instant.now()` taken once at the start of the recomputation (not the span instant), and `latest_source_received_at` by `LatestSourceReceivedAtResolver` over remaining members' versions. The old tier is `tierFor` of L's old score, defaulting to 0.5 when absent. Orphaned outcomes compute no score.

## Downstream propagation

`golden_record.updated` is emitted and the record exposes its `status`; the bundle notes that no project rule says how an `active → orphaned` transition is notified downstream. Match compares against `golden_data`, so stale values on L could otherwise attract matches.

None: `orphaned` already exists and `deactivation_reason` is free text.

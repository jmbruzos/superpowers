# La ficha que pierde un miembro se recalcula — neutral summary

## Scope

Covers the ForceRule move in `PersistenceStepHandler.persistMembership`, the one path that today closes a span on an active golden record without recalculating its data. Consolidation, orphan spans and manual merge are excluded, since the losing record is not active; review-case resolution does not move membership today and is noted as a future caller. Unmerge already recomputes and is left unchanged; aligning its pin ordering, reason and `previous` handling is deferred. A record that survived a manual merge (an active `GOLDEN_TO_GOLDEN` ForceRule pointing at it) is also recomputed in full: the exclusion protecting it from re-survivorship covers rule changes, not membership changes, and unmerge already recomputes it.

## Recomputation mechanism

`SurvivorshipFold`, a new stateless class with a static `fold`, receives the private body of `StewardshipService.reSurvivorshipFromSources` unchanged: the first Silver version merges in `create` mode, later ones in `update` mode over the accumulated result; an empty list returns `null`. `StewardshipService` delegates with an unchanged constructor. A new bean, `MemberExitRecalculator.onMemberExit`, requires an existing transaction, re-reads the losing record with `findByIdForUpdate`, and returns `SKIPPED_NOT_ACTIVE` if it is missing or not active. Otherwise it deactivates pins, reads current members, loads all their Silver versions via `findVersionsOfMembers`, folds them with the injected `MergeEngine`, and rewrites `golden_data`, `field_lineage`, `latest_source_received_at`, `quality_score` and audit fields before `saveAndFlush` (outcome `RECOMPUTED`). If members remain but none has a Silver version, fields whose lineage points to the departed record (matched as pins are; a `stewardship`-sourced legacy-pin entry matches by id alone) are pruned from data and lineage at JSON level, the rest kept, freshness set to null, and a warning logged; this is also reported as `RECOMPUTED`.

## Field lineage and `previous`

After the fold, `previous` is rebuilt against persisted state: a field whose value changed gets the stored value, the stored entry's source and the recalculation instant; an unchanged one gets `previous = null`. No lineage entry may name the departed record. Unmerge's `previous = null` behaviour stays.

## Losing the last member

With no current members the status becomes `orphaned`; `golden_data`, `field_lineage` and `quality_score` are kept unchanged as a read-only historical snapshot and no score is recomputed. Key removal and source count dropping to zero come from the existing cleanup and refresh, checked only as regression.

## Pins/overrides/ForceRules on the departed record

Active source pins on the losing record that pin the departed record — full identity, or id alone for a legacy pin with no recorded source — are deactivated with reason `auto_member_exit` and actor `system:pipeline`, flushed before the fold so the engine no longer applies them. A remaining member's pin stays and applies. Value overrides are not addressed. A manual-merge survivor's `GOLDEN_TO_GOLDEN` ForceRule is untouched. Rules targeting a newly orphaned record are out of scope.

## Locking/concurrency/retries

The recomputation runs inside the persistence transaction, under the `FOR UPDATE` lock already held on the losing record, after `move` and `cleanUpAfterLosingMember` and before the native-update `refreshSourceCounts`, so a later flush cannot overwrite the count. Saving increments the version. Any exception rolls back the whole step — span, keys, both records — under the existing retry policy. An optimistic-locking failure goes back to Merge and retries with membership re-resolved. The longer lock is an accepted cost, to be measured.

## Events and cache invalidation

All events are published after commit (immediately when no synchronization is active); failures are logged, and a rollback publishes nothing. In both `RECOMPUTED` and `ORPHANED` outcomes the losing record is evicted and `golden_record.updated` is published with the existing emitter's payload; each deactivated pin publishes `FieldOverrideAutoDeactivated`. `GoldenRecordQualityChanged` fires only on a tier crossing in the recomputed case, never when orphaned. A `PRODUCED` lineage edge (run to losing record, `action = member_exit`) is added when the record is written, including when orphaned. The spec's component list and data flow still say the edge is added only for `RECOMPUTED`; its amended rule, the plan and the tasks add it for `ORPHANED` too. The persistence step output records the outcome.

## Quality score and tier

`QualityScoreResolver` computes the score at the recalculation instant, not the moved record's receipt time; freshness comes from `LatestSourceReceivedAtResolver` over remaining members' versions. The previous tier uses the previous score, or 0.5 if none, matching the existing tier-change guard.

## Downstream propagation

A project rule says an orphaned record does not propagate downstream; `golden_record.updated` is still published on orphaning because it is the cache-invalidation channel. No business event exists for orphaning; one is to be proposed later. The existing emitter's payload (id and entity type only) is used, though it diverges from the event catalogue.

## Tests planned

Unit tests for the fold (empty, single, three versions). Recalculator unit tests with a real merge engine: the departed's field passes to the remaining member with `previous`, unchanged fields get null `previous`, score at the clock instant; orphaning with data untouched; non-active and missing records write nothing; pin deactivation (full and legacy) before the fold; pruning, including legacy-pin lineage; tier crossing; after-commit registration and no publication on rollback. Handler tests: call before `refreshSourceCounts`, `PRODUCED` edge rules, failure propagation, other branches not calling it. Integration tests: two-member move (score against a reference calculation), sole-member orphaning, pin fallback, full rollback on forced failure. Existing stewardship tests pass unchanged; 80% line coverage on the new classes.

## Migrations

Not addressed for the chosen design; the rejected flag-and-sweep alternative was turned down partly because it needed a migration and a scheduler.

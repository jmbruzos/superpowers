# La ficha que pierde un miembro se recalcula — neutral summary

## Scope

Covers the ForceRule move in `PersistenceStepHandler.persistMembership`, the only span closure that today leaves an active record losing a member with only keys, cache and source count updated. Consolidation and orphan-span moves are excluded, since their previous record is absorbed, missing, deleted or orphaned; manual merge is out of scope; review resolution closes no spans in production code. Unmerge keeps its flow and only delegates its chain to the shared component. No production code creates `SOURCE_TO_GOLDEN` rules today; the gap is reached through stored rules and a future source-to-golden operation. Recomputing a manual-merge survivor is not addressed.

## Recomputation mechanism

Synchronous, in the transaction that closes the span; deferred marking and event-driven recompute were rejected. `MemberSurvivorshipChain`, extracted verbatim from `StewardshipService.reSurvivorshipFromSources` and not a Spring bean, merges the first Silver version as `create` and the rest as `update` over the accumulated result; both `StewardshipService` overloads delegate to it, so the result equals admin re-survivorship. `LosingMemberRecomputer`, a bean, returns an outcome of `RECOMPUTED`, `ORPHANED`, `SKIPPED` or `NOT_ACTIVE`: it writes nothing for a missing or non-active record; otherwise it reads current members, loads their versions in deterministic order via `findVersionsOfMembers`, chains them with the merge-engine bean (so overrides apply) and the run's survivorship config, and writes data, lineage, freshness, score, the run's `schema_version`, `source_count` as the number of current spans, and audit fields via `saveAndFlush`. Members without versions contribute nothing (warning); if none has versions the outcome is `SKIPPED` with no write. It is called after the move and key cleanup and before `refreshSourceCounts`, whose native update would otherwise be overwritten by a later flush of the stale entity. Injection is optional. Despite a project rule forbidding JPA imports outside the persistence module, the new components follow the module's existing precedent.

## Field lineage and `previous`

Lineage comes solely from chaining the remaining members' versions, starting from `create` with no existing data or lineage; no `field_lineage` entry may carry the departed record's source and id. The `previous` field is not addressed.

## Losing the last member

Status becomes `orphaned`, `golden_data` and `field_lineage` become `{}`, `quality_score` and `latest_source_received_at` null, source count zero, `schema_version` unchanged; existing cleanup removes keys. Keeping the data as a historical read was rejected: history can be rebuilt from closed spans and immutable Silver versions. One project rule says such a record becomes `absorbed`, another says `orphaned`; the design follows `orphaned` and defers reconciliation.

## Pins/overrides/ForceRules on the departed record

Source pins to the departed record stay active and have no effect, since the engine falls back to survivorship. Value overrides apply normally. Rules on a record that becomes orphaned (overrides, ForceRules, suppressions) and open review cases on it are left untouched; Match already ignores a ForceRule targeting an orphaned record.

## Locking/concurrency/retries

Runs under the `FOR UPDATE` lock the caller already holds; `saveAndFlush` increments `@Version`, and an optimistic-lock failure follows the existing conflict path back to merge. Any other exception propagates as a Persistence failure: the existing transaction rolls back the whole move and the orchestrator's retry and dead-letter policy applies. Outcomes are cleared at the start of each Persistence attempt and in `clearMergeOutput()`, so only the committing attempt leaves results.

## Events and cache invalidation

Persistence publishes nothing to the event bus for the losing record. Outcomes travel in `PipelineContext` to Propagation (`AsyncPipelineExecutor`, `IngestService`), which after a `completed` run emits `golden_record.updated` for `RECOMPUTED` and `ORPHANED`, the cross-pod cache invalidation path; emission failures are logged, not propagated. The in-process `evictAfterCommit` stays in Persistence. For those two outcomes Persistence also adds a `PRODUCED` lineage edge from the run to the record (`reason: lost_member`); no edge is rewritten.

## Quality score and tier

The score uses the shared resolver at an evaluation instant taken in `PersistenceStepHandler`, never inside the resolver; freshness is resolved over the remaining versions only. A tier crossing on `RECOMPUTED` emits `GoldenRecordQualityChanged` and increments the tier-change metric; the previous tier uses 0.5 when no score existed. Orphaned records have no score and no tier event. The plan computes the previous tier in the recomputer rather than in Propagation, a stated interface deviation from the spec with the same rule.

## Downstream propagation

Not addressed, except that the spec argues emitting `golden_record.updated` for an orphaned record, which a rule says does not propagate downstream, is cache invalidation and status notification, not data propagation.

## Tests planned

Unit tests cover the chain (empty list, ordering) and the recomputer (every derived column, a member without versions, orphaning, skipping, not-active). Handler tests check ordering before `refreshSourceCounts`, no call on consolidation or orphan moves, exception propagation, unchanged behaviour without the component, per-attempt clearing, and the lineage edge only for two outcomes. Propagation tests check update events, a tier event only on a crossing, and nothing for a non-`completed` run. Integration tests move one of two members and compare data, four lineage keys (excluding `resolved_at`), score, freshness and a replaced `schema_version` sentinel against the chain over the remaining member; move a sole member and check orphaning; and add an unmerge lineage guard that already passes. A full build with at least 80% line coverage closes the work.

## Migrations

None planned. The rejected deferred-marking alternative would have needed one; the status column has no check constraint blocking `orphaned`.

# La ficha que pierde un miembro se recalcula — neutral summary

## Scope

Covers the ForceRule move in the pipeline (`PersistenceStepHandler.persistMembership`), which today only regenerates the losing record's blocking keys and source count. Unmerge already recomputes correctly and keeps that behaviour through the shared calculator, gaining a lineage test. Manual merge, consolidation and orphan moves are excluded, since their losing record is absorbed, missing, deleted or orphaned. Review resolution writes no span closures today; the rule is to be documented so a future implementation applies it. A manual-merge survivor (`GOLDEN_TO_GOLDEN`) is also recomputed, since the manual merge does not fix its data; a rule listing manual merge as not re-running survivorship is read as an enumeration, not an invariant. No new membership moves are added.

## Recomputation mechanism

Calculation lives in Merge and Persistence writes under a version guard. `MemberSurvivorship`, a new stateless calculator in `mdm-merge-engine`, chains the first `MemberVersion` as `create` and the rest as `update` exactly as `StewardshipService.reSurvivorshipFromSources` does (trust 1.0, quality or 0.8), with a run-id supplier called once per request; it returns null for an empty list. All three copies of the chain in `StewardshipService`, including `reSurvivorshipFromSourcesWithOverride`, delegate to it while keeping order and request ids. The `SourceRecordVersionReader` port gains `findVersionsOfMembers` and a `qualityScore` on `SourceRecordVersion`, so the pipeline needs no JPA imports, honouring a project rule. `MergeStepHandler` computes a `LosingGoldenRecordRecompute` only when membership is `FORCED` with a non-null conflicting record L, the action is `update`, the target differs from L, and L is active (checked before reading members). It reads L's current members minus the full incoming identity, loads all their Silver versions, and runs the calculator with the merge-engine bean (applying L's overrides) and the run's survivorship config; with no versions the result is null. The recompute travels in `PipelineContext`. In the ForceRule branch after the move, Persistence always writes L: recomputed data, lineage, freshness and score; or, with no versions, only freshness (null if none), keeping data and score, with a warning. Errors in Merge fail the Merge step with no partial state.

## Field lineage and `previous`

The chain starts from `create` with null existing data and lineage, so no `field_lineage` entry of L may cite the departed record, except a value override attributed to stewardship. The `previous` field is not addressed.

## Losing the last member

L becomes `orphaned`; `golden_data` and `field_lineage` are kept as a read-only historical snapshot; source count drops to zero and keys are removed. One project rule says such a record becomes `absorbed`, another `orphaned`; the design follows `orphaned` and leaves reconciliation, and how an orphaned record returns to active, for later.

## Pins/overrides/ForceRules on the departed record

A new `DepartedMemberPinDeactivator` deactivates L's active source pins on the departed identity (by pinned id and, when set, pinned source; a legacy pin without source matches by id; a pin with a null pinned id is ignored), with reason `member_left` and actor `system:pipeline`, mirroring unmerge. Pins on remaining members stay active. ForceRules targeting L are not touched; Match already ignores one whose target is orphaned. The survivor's `GOLDEN_TO_GOLDEN` rule is not touched.

## Locking/concurrency/retries

Persistence locks the target and L in ascending id order. A guard requires L to exist, be active and match the version read in Merge; a mismatch, a non-active L or a null expected version evicts L and throws `OptimisticLockingFailureException`, so the orchestrator re-resolves membership and recomputes. L is always written, bumping its version, so two concurrent moves from L cannot both pass the guard. `clearMergeOutput()` drops the recompute so a retry does not reuse it.
## Events and cache invalidation

Persistence emits no events; it stores a `LosingGoldenRecordWrite` (result, previous and new score and tier, deactivated pins) in the context. After a `completed` run, `IngestService` and `AsyncPipelineExecutor` emit, through `LosingGoldenRecordEvents`, `golden_record.updated` for L (cross-pod invalidation), `GoldenRecordQualityChanged` when the tier crosses, and `FieldOverrideAutoDeactivated` per pin with no survivor id. Failed or dead-letter runs emit nothing for L. The existing in-process `evictAfterCommit(L)` is kept.

## Quality score and tier

Merge computes the score with the shared resolver over the result and the freshness resolved on remaining versions only, never combined with the persisted value, using the current instant. The previous tier comes from L's prior score (0.5 if null). Orphaned and no-version outcomes carry no new score or tier and emit no tier event. The spec reads the previous score under lock in Persistence; the plan uses the value read in Merge, arguing the version guard makes them equal.

## Tests planned

Unit tests cover the calculator (empty, single, ordered chaining, quality defaults, one run-id call per request, parity with the real engine under `most_recent`); the spec's "null versus given run id" case is replaced by the supplier. Merge tests cover the trigger condition, exclusion of the full incoming identity, orphaning, members without versions, freshness ignoring the persisted value, and clearing on retry. Persistence tests cover recomputed, orphaned and no-version writes, the three conflict cases, ignoring the recompute without a move, legacy and null pins, and no events from Persistence. Emitter tests cover tier crossing, per-pin events and failed or dead-letter runs. Integration tests against Postgres cover recompute with a dropped field and changed score, sole-member orphaning, pin deactivation, a version conflict forced mid-run that retries with fresh data, and an unmerge lineage assertion, with a full build.

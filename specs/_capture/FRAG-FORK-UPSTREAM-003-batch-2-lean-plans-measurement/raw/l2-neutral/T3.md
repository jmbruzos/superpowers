# La ficha que pierde un miembro se recalcula — neutral summary

## Scope

Covers the ForceRule move (`SOURCE_TO_GOLDEN`) handled by `PersistenceStepHandler.persistMembership`'s `FORCE_RULE` branch, where the losing record L stays active but today only has its keys and source count cleaned, keeping values and lineage won by the departed record. Manual merge, automatic consolidation and spans to a missing/deleted/orphaned target are excluded, since the losing record is no longer live; the `CONSOLIDATION` and orphan branches do not call the new component. Review-case resolution is out of scope, since it closes no spans today. The bundle notes the product creates no `SOURCE_TO_GOLDEN` rules today (only legacy rows and test inserts reach the branch). Unmerge keeps its normal path but gains a fix for the branch where the remaining members have no Silver versions. A manual-merge survivor is covered, but only the departed record's fields are touched.

## Recomputation mechanism

Recomputation is targeted, per field, synchronous, in the same transaction. `SurvivorshipReplay`, a non-bean class, is extracted unchanged from `StewardshipService`'s private six-argument `reSurvivorshipFromSources`: first Silver version merged in `create` mode, the rest in `update` mode, returning null for no versions; the private method delegates to it and `reSurvivorshipFromSourcesWithOverride` is untouched. A new bean, `LosingMemberRecomputer.recompute`, with the record already locked and the span closed: returns `NOT_ACTIVE` if the record is missing or not active; deactivates pins on the departed; builds an affected set A from lineage entries naming the departed (matching `source` and `source_record_id`) plus the fields of the deactivated pins; returns `EMPTIED` if no members remain; otherwise replays all remaining members' versions (via `findVersionsOfMembers`, deterministic order) with the `MergeEngine` bean, which still applies active overrides and pins, and copies into L only the A fields from the result, removing any field the replay lacks. Fields outside A are untouched, justified by a project rule that schema changes are not applied retroactively and another that a manual-merge survivor is not re-survived. Empty A gives `UNCHANGED`, no write. If members remain but none has Silver versions, A fields are removed, all active source pins deactivated (reason `auto_pin_unresolvable`) and their fields removed, with a WARN (`STRIPPED`). Full recomputation, a `needs_recompute` sweep and an async consumer were rejected. A static `patch` function and `recomputeFields` (targeted refresh of given fields, no pin step) are exposed. The plan adds `operationId` and `eventSource` to `LosingMemberRequest`, beyond the spec's signature.

## Field lineage and `previous`

Each changed affected field gets `previous = {value, source, changed_at}` with the prior value, since the replay starts from `create` and does not carry it. No resulting lineage entry may name the departed record. Value-override lineage (`source = "stewardship"`, operator id) never enters A.

## Losing the last member

L becomes `absorbed`, not `orphaned`: the bundle follows the pipeline rule over a conflicting survivorship rule. `absorbEmptiedGoldenRecord` saves the status, writes an `ABSORBED_INTO` L → F edge (`reason: manual`, `pipeline_run_id`, `absorbed_at`), migrates L's overrides to F with `ConsolidationOverrideMigrator.migrate`, then calls `recomputeFields` on F for those override fields, and publishes `golden_record.consolidated` after commit. Keys are removed and source count is zero. Rules targeting L are followed via `ABSORBED_INTO`.

## Pins/overrides/ForceRules on the departed record

Active `SOURCE_PIN` overrides pinning the departed (full identity, or id alone when `pinned_source` is null) are deactivated with reason `auto_member_left`, actor `system:pipeline`, and `FieldOverrideAutoDeactivated` after commit; their field is re-resolved. Value overrides stay active and their fields do not change. A manual-merge survivor's `GOLDEN_TO_GOLDEN` ForceRule stays active; no project rule covers this case.

## Locking/concurrency/retries

L is already locked `FOR UPDATE` before the move; `recompute` does not re-lock. A concurrent merge that read L conflicts on the version guard and retries. Any exception from `recompute` or the absorption propagates and rolls back the whole persistence transaction; optimistic-lock or lock errors retry, other errors fail the step. Replay cost under the lock has no budget; a duration log is added.

## Events and cache invalidation

On `RECOMPUTED`/`STRIPPED`: `saveAndFlush`, `evictAfterCommit`, `golden_record.updated` after commit exactly once when something changed (current emitter signature, no reason), never on `UNCHANGED`, and `GoldenRecordQualityChanged` on a tier crossing. Pin-deactivation events and `golden_record.consolidated` also fire after commit. Events are best-effort.

## Quality score and tier

On `RECOMPUTED`/`STRIPPED`, `quality_score` is recomputed by `QualityScoreResolver` at an `evaluationInstant` (`Instant.now()` from the handler), and `latest_source_received_at` by `LatestSourceReceivedAtResolver` over remaining members' versions; the tier check uses the same criterion as `maybeEmitQualityTierChange`. In unmerge's null-result branch the score is also recomputed over the patched data.

## Downstream propagation

Not addressed. The bundle's rationale notes that match compares incoming records against the candidate's `golden_data`, so stale values on L would affect new matches.

## Tests planned

Unit tests: `SurvivorshipReplayTest` (empty list, create/update chaining, 0.8 default quality); `LosingMemberRecomputerPatchTest` (null replay, replay values, missing field, `previous`, untouched fields, legacy lineage entries, value override excluded); `LosingMemberRecomputerTest` (each outcome, targeted fields, pins full and legacy, stripping with WARN, events only after commit, exactly-once update event, score/freshness/evict, all versions replayed, null lineage). `PersistenceStepHandlerTest`: call order before `refreshSourceCounts`, absorption with edge, migration and F refresh, failure propagation, consolidation/orphan branches and a linked re-ingest not recomputing, ForceRule to an absorbed target. Unmerge unit test for the null branch plus an `StewardshipFlowsIT` lineage assertion. Integration tests: targeted recompute, manual-merge survivor, sole-member absorption, pin deactivation. Coverage ≥80% per new class via explicit JaCoCo, full `mvn verify`, spec validation. The spec names the integration class `LosingMemberIT`; the tasks put these tests in `SourceIdentityPipelineIT`.

None: no Flyway migration and no new Maven dependencies.

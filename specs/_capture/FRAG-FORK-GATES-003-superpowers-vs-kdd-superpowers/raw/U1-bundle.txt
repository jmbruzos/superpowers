# WRK-PLAN-MDM-MEMBER-LOSS-001 — La ficha que pierde un miembro se recalcula

## Approach

**Goal:** que la ficha activa que pierde un miembro (movimiento por ForceRule hoy; cualquier cierre de tramo mañana)
se recalcule con survivorship sobre sus miembros vigentes en la misma transacción, que su linaje deje de nombrar al
registro que salió y que, sin miembros, pase a `orphaned`.

**Architecture:** se extrae el encadenado create→update de `StewardshipService.reSurvivorshipFromSources` a
`SurvivorshipReplay` (mdm-ingest-service) y el gateway delega en él. Un componente nuevo,
`LosingGoldenRecordRecomputer` (mdm-ingest-service), aplica la regla "ficha que pierde un miembro": pins, replay,
frescura, score, `source_count`, estado, claves y eventos tras commit. `PersistenceStepHandler.persistMembership` lo
invoca tras `membershipRepository.move(...)` en lugar de `cleanUpAfterLosingMember`. El unmerge no cambia (ya cumple);
se fija con un test de regresión.

**Tech Stack:** Java 21, Spring Boot 3.4, Spring Data JPA/Hibernate, PostgreSQL 16, JUnit 5 + AssertJ + Mockito,
Testcontainers.

**Spec:** `specs/work/WRK-SPEC-MDM-MEMBER-LOSS-001-la-ficha-que-pierde-un-miembro-se-recalcula.md` — el plan argumenta
desde la spec; los ejecutores leen ambos.

**Comandos** (desde `src/`, con `JAVA_HOME` de Java 21): `mvn -q test -pl <módulo> -am -Dtest=<Clase>
-Dsurefire.failIfNoSpecifiedTests=false` para unitarios; `mvn -q verify -pl mdm-app -am -Dit.test=<ClaseIT>
-Dtest=none -DfailIfNoTests=false` para un IT (Docker en marcha).

# WRK-SPEC-MDM-MEMBER-LOSS-001 — La ficha que pierde un miembro se recalcula

Cierra RFC-PIPE-039 (cluster `work:manual-unification`, ADR-011). Pariente de OQ-1 de
WRK-SPEC-MDM-SOURCE-IDENTITY-001 (el merge incremental no retira valores), que queda fuera: aquí solo se trata la
salida de un miembro, no el cambio de valores de un miembro que se queda.

## Problem Statement

Cuando un registro de origen sale de una ficha (se cierra su tramo en la xref, ADR-022 §Decisión 2), la ficha que lo
pierde debe dejar de mostrar lo que ese registro aportaba. Estado actual del código (rama `main`, 2026-09-29):

| Operación que cierra un tramo en una ficha activa | ¿Recalcula la ficha que pierde el miembro? |
|---|---|
| Unmerge (`StewardshipService.unmerge`) | **Sí**: `reSurvivorshipFromSources` sobre las versiones de los miembros restantes; escribe `golden_data`, `field_lineage`, `latest_source_received_at` y `quality_score`; desactiva los pins del separado. |
| Movimiento por ForceRule en el pipeline (`PersistenceStepHandler.persistMembership`, `kind = FORCE_RULE`) | **No**: `cleanUpAfterLosingMember` solo repone y borra blocking keys; `source_count` baja pero `golden_data` y `field_lineage` conservan los valores y el linaje del registro que salió. |
| Resolución de un caso de revisión (`review_resolution`) | No cierra tramos hoy (`MembershipOperationKind.REVIEW_RESOLUTION` no tiene llamadores); la WRK-SPEC de la review queue lo hará. |
| Consolidación y merge manual (fichas absorbidas) | No aplica: la ficha que pierde miembros pasa a `merged`/`absorbed`, no sigue activa. |
| Tramo hacia ficha inexistente/`deleted`/`orphaned` (`membership_orphan`) | No aplica: la ficha no está activa. |

Consecuencia (RFC-PIPE-039 §Impact): un consumidor lee en la ficha L un email o un NIF que ya vive en la ficha F.
Además, si la ForceRule saca al único miembro de L, L queda `active` con `source_count = 0`, contra la transición
`active → orphaned` de DOM-MDM-SURVIVORSHIP-001 §2, que nadie implementa.

## Decisiones (brainstorming 2026-09-29; aprobadas por human:ab-test)

- **D1 — Recálculo síncrono** en la misma transacción que cierra el tramo, bajo el `FOR UPDATE` que esa transacción ya
  toma sobre la ficha que pierde el miembro. Descartados: marca `needs_recompute` + barrido (migración, planificador y
  una ventana de lecturas obsoletas) y evento tras commit hacia el re-survivorship del gateway (los eventos son
  best-effort: uno perdido deja la ficha obsoleta para siempre).
- **D2 — Un único componente** aplica la regla "ficha que pierde un miembro" (`LosingGoldenRecordRecomputer`,
  `mdm-ingest-service`); absorbe la limpieza de blocking keys que hoy hace `cleanUpAfterLosingMember`. Toda operación
  presente o futura que cierre un tramo en una ficha activa lo invoca.
- **D3 — Misma entrada y mismo encadenado que el re-survivorship y el unmerge**: todas las versiones en Silver de los
  miembros vigentes (`StagedRecordJpaRepository.findVersionsOfMembers`, mismo orden), encadenadas `create` → `update`
  con el `MergeEngine` bean (con `FieldOverrideProvider`: respeta value overrides y pins vigentes). El encadenado se
  extrae de `StewardshipService.reSurvivorshipFromSources` a `SurvivorshipReplay` (`mdm-ingest-service`) y el
  gateway delega en él sin cambiar de comportamiento.
- **D4 — Sin miembros vigentes → `orphaned`**: la ficha pasa a `status = orphaned`, `source_count = 0`, sin blocking
  keys; `golden_data` y `field_lineage` se conservan como instantánea histórica de solo lectura (DOM-MDM-SURVIVORSHIP-001
  §2: "Sí (solo lectura histórica)"; mismo criterio que las fichas `merged`). No se recalcula el quality score.
- **D5 — Supervivientes de un merge manual también se recalculan.** La exclusión de §3.8 del re-survivorship bajo
  demanda protege el `golden_data` que decidió el steward frente a un recálculo sin motivo; aquí el motivo es que un
  miembro ya no pertenece a la ficha. La ForceRule `GOLDEN_TO_GOLDEN` sigue activa.
- **D6 — Pins al registro que salió**: los `SOURCE_PIN` activos de la ficha que pierde el miembro cuyo registro fijado
  es la identidad que salió (identidad completa; pin legado sin `pinned_source`: por id) se desactivan con
  `deactivation_reason = auto_member_left` y evento `FieldOverrideAutoDeactivated` tras commit, como hace el unmerge
  con `auto_unmerge`. Los `VALUE_OVERRIDE` se conservan.
- **D7 — Unmerge no cambia**: ya cumple; se añade un test de regresión sobre el linaje.

## Proposed Change

### 1. `SurvivorshipReplay` (mdm-ingest-service, `com.mdm.ingest.survivorship`)

`MergeResult replay(List<StagedRecordEntity> versions, SurvivorshipConfig config, String tenantId, String grId,
MergeEngine engine)` y la sobrecarga sin `engine` (usa el bean). Devuelve `null` con lista vacía. Mismo cuerpo que
`StewardshipService.reSurvivorshipFromSources` (calidad por defecto `0.8`, confianza `1.0`, `pipelineRunId`
`re-survivorship-<uuid>`). `StewardshipService` delega sus dos sobrecargas en él; los previews con motor efímero pasan
su motor.

### 2. `LosingGoldenRecordRecomputer` (mdm-ingest-service, `com.mdm.ingest.survivorship`)

```java
Outcome recompute(LossContext loss)
record LossContext(String tenantId, String goldenRecordId, List<SourceRecordIdentity> departed,
                   SurvivorshipConfig survivorshipConfig, String actor, Instant evaluationInstant)
enum Outcome { NOT_ACTIVE, ORPHANED, RECOMPUTED, NO_SOURCES }
```

Precondición: el llamante ya cerró los tramos de `departed` y tiene la ficha bloqueada (`FOR UPDATE`). Pasos:

1. Carga la ficha por id y tenant. Si no existe o no está `active` → limpieza de claves (paso 5) y `NOT_ACTIVE`.
2. Miembros vigentes `SourceMembershipRepository.findCurrentMembers(tenant, gr)`.
3. Sin miembros → `status = orphaned`, `sourceCount = 0`, `updatedAt/By`; `saveAndFlush`; limpieza de claves;
   evento `GoldenRecordUpdated` (`reason: member_left`, `status: orphaned`) tras commit; `ORPHANED`.
4. Con miembros → desactiva pins (D6); `SurvivorshipReplay` sobre `findVersionsOfMembers`; escribe `golden_data`,
   `field_lineage`, `latest_source_received_at` (`LatestSourceReceivedAtResolver` sobre las versiones),
   `quality_score` (`QualityScoreResolver`, instante `evaluationInstant`), `sourceCount = miembros.size()`,
   `updatedAt/By`; `saveAndFlush`; limpieza de claves; tras commit: `GoldenRecordUpdated` (`reason: member_left`) si
   cambió `golden_data` o el score, y `GoldenRecordQualityChanged` si cruza de tier (misma guarda que el pipeline,
   DOM-MDM-SURVIVORSHIP-001 §3.7.3); `RECOMPUTED`. Si el replay devuelve `null` (ningún miembro tiene filas en
   Silver): no se tocan `golden_data`, `field_lineage` ni el score; sí `sourceCount`, pins y claves; `warn` y
   `NO_SOURCES` (mismo criterio "sin sources resolubles" que el re-survivorship, `skipped`: no se inventa un dato).
5. Limpieza de claves = cuerpo actual de `cleanUpAfterLosingMember`: `ensureMemberKeys` de cada miembro vigente y
   `deleteStaleEntries(tenant, gr, miembros)`.

Invalidación de caché: `cacheEvictor.evictAfterCommit(gr)` en todos los casos.

### 3. Pipeline

`PersistenceStepHandler.persistMembership`: donde hoy llama a `cleanUpAfterLosingMember(tenant, previous)` tras
`membershipRepository.move(...)`, llama a `recomputer.recompute(new LossContext(tenant, previous, List.of(id),
ctx.getSurvivorshipConfig(), "pipeline:" + run, Instant.now()))`. `cleanUpAfterLosingMember` desaparece.
`refreshSourceCounts` sigue al final (idempotente; el recomputer ya dejó el mismo valor en la entidad, así que un
flush posterior no lo pisa con uno obsoleto). La ficha `previous` ya está bloqueada (`lockGoldenRecordsBeforeMove` o
la rama `!locked.contains(previous)`); su versión sube, y un pipeline concurrente que la escriba con la versión vieja
choca con la guarda de ADR-020 y reintenta desde Merge (DOM-MDM-PIPELINE-001 §6.5).

`ctx.getSurvivorshipConfig()` sirve: la ficha que pierde el miembro es del mismo `entity_type` (la identidad lo incluye).

### 4. Contrato para operaciones futuras

Al consolidar: DOM-MDM-PIPELINE-001 (§10.6/§10.8 y la tabla de §6.3 sobre `force_rule`) y DOM-MDM-SURVIVORSHIP-001 (§2
transición `active → orphaned`, que pasa a decir "cuando el último miembro vigente sale por cualquier operación", y
§3.8 nueva fila de trigger "salida de un miembro — automático") recogen la regla: **toda operación que cierra un tramo
en una ficha activa invoca `LosingGoldenRecordRecomputer` en su transacción**. La WRK-SPEC de la review queue la hereda
para `review_resolution`.

### 5. Pruebas

- Unitarias: `SurvivorshipReplayTest` (lista vacía, un miembro, encadenado de varios); `LosingGoldenRecordRecomputerTest`
  (no activa; sin miembros → orphaned; recálculo con campo que solo aportaba el que salió → desaparece; pins
  desactivados solo para la identidad que salió, incluido pin legado; eventos tras commit; score/tier;
  replay `null`); `PersistenceStepHandlerTest` (un movimiento FORCE_RULE invoca el recomputer con `previous` y la
  identidad; sin movimiento no lo invoca).
- IT (`mdm-app`, Testcontainers): ampliación de `SourceIdentityPipelineIT.forceRuleMovesLinkedRecord` y casos nuevos
  en `MemberLossIT`: ForceRule mueve X1 de L a F → el `email` de L es el de X2 y ningún `field_lineage` de L nombra
  `crm:X1`; ForceRule saca al único miembro → `orphaned`, sin claves, sin tramos; pin a X1 desactivado
  (`auto_member_left`); superviviente de merge manual recalculado con la ForceRule `GOLDEN_TO_GOLDEN` activa;
  aislamiento por tenant (mismos datos en T1 y T2, solo cambia la ficha de T1); concurrencia (ingesta de X2 en L
  mientras X1 sale: al terminar, `golden_data` de L = replay sobre sus miembros finales).
- Regresión de unmerge: tras separar un miembro, ninguna entrada de `field_lineage` de la ficha original nombra al
  separado.

## Acceptance Criteria

- [ ] AC1. Tras un movimiento por ForceRule desde una ficha activa L que conserva miembros, `golden_data` y
  `field_lineage` de L son los que produce `SurvivorshipReplay` sobre las versiones de sus miembros vigentes
  (salvo `resolved_at`); ninguna entrada de `field_lineage` de L (ni su `previous`) nombra la identidad que salió.
- [ ] AC2. Un campo que solo aportaba el registro que salió desaparece de `golden_data` de L, salvo `VALUE_OVERRIDE`.
- [ ] AC3. `latest_source_received_at` y `quality_score` de L se recalculan sobre los miembros vigentes;
  `GoldenRecordQualityChanged` se emite si cruza de tier y `GoldenRecordUpdated` (`reason: member_left`) si cambian
  datos o score, ambos después del commit.
- [ ] AC4. Si L se queda sin miembros vigentes: `status = orphaned`, `source_count = 0`, sin filas en
  `blocking_key_entries`, sin tramos vigentes; `golden_data` sin cambios.
- [ ] AC5. Los `SOURCE_PIN` activos de L sobre la identidad que salió quedan inactivos con `auto_member_left`; los
  pins a otras identidades y los `VALUE_OVERRIDE` siguen activos.
- [ ] AC6. Un superviviente de merge manual que pierde un miembro se recalcula y su ForceRule `GOLDEN_TO_GOLDEN` sigue
  activa.
- [ ] AC7. Una ingesta concurrente en L mientras un miembro sale de L termina (con o sin reintento) con L igual al
  replay sobre sus miembros finales.
- [ ] AC8. Con datos idénticos en dos tenants, el recálculo en un tenant no lee ni modifica fichas, pins ni claves del
  otro.
- [ ] AC9. Unmerge: ninguna entrada de `field_lineage` de la ficha original nombra a un separado (regresión); los ITs
  de unmerge, re-survivorship y previews existentes siguen en verde sin tocar sus aserciones.
- [ ] AC10. No queda `cleanUpAfterLosingMember`; `SurvivorshipReplay` es el único encadenado create→update de
  re-survivorship en producción, salvo `reSurvivorshipFromSourcesWithOverride` (preview de corrección: sustituye en
  memoria el dato de una fila y no es re-survivorship).

- OQ-1. ¿Debe `orphaned → active` reactivarse si la ForceRule que sacó al miembro se desactiva y el registro vuelve?

- OQ-2. Coste del replay en fichas con muchos miembros y versiones. Los movimientos por ForceRule son raros; si el
  benchmark lo exige, limitar a la última versión por miembro sería un cambio de semántica del re-survivorship y va a
  un RFC aparte.

package com.mdm.ingest.survivorship;

import com.fasterxml.jackson.core.type.TypeReference;
import com.fasterxml.jackson.databind.ObjectMapper;
import com.mdm.core.domain.merge.MergeResult;
import com.mdm.core.domain.schema.SurvivorshipConfig;
import com.mdm.engine.merge.MergeEngine;
import com.mdm.engine.merge.MergeRequest;
import com.mdm.persistence.entity.StagedRecordEntity;
import org.springframework.stereotype.Component;

import java.util.List;
import java.util.Map;
import java.util.UUID;

/**
 * Re-ejecuta survivorship sobre versiones de Silver: la primera en modo {@code create}, el resto en {@code update}
 * sobre el resultado acumulado. Unico encadenado de re-survivorship (re-survivorship bajo demanda, unmerge, previews
 * y la ficha que pierde un miembro, WRK-SPEC-MDM-MEMBER-LOSS-001 D3). Extraido sin cambios de
 * {@code StewardshipService.reSurvivorshipFromSources}.
 *
 * <p>El motor por defecto es el bean de Spring, con el {@code FieldOverrideProvider} real: respeta value overrides y
 * pins vigentes. Los previews pasan un motor efimero.
 */
@Component
public class SurvivorshipReplay {

    private static final TypeReference<Map<String, Object>> MAP_TYPE_REF = new TypeReference<>() {};

    private final MergeEngine mergeEngine;
    private final ObjectMapper objectMapper;

    public SurvivorshipReplay(MergeEngine mergeEngine, ObjectMapper objectMapper) {
        this.mergeEngine = mergeEngine;
        this.objectMapper = objectMapper;
    }

    /** {@link #replay(List, SurvivorshipConfig, String, String, MergeEngine)} con el motor por defecto. */
    public MergeResult replay(List<StagedRecordEntity> versions, SurvivorshipConfig config,
                              String tenantId, String goldenRecordId) {
        return replay(versions, config, tenantId, goldenRecordId, mergeEngine);
    }

    /**
     * @return resultado del ultimo paso del encadenado, o {@code null} si no hay versiones
     */
    public MergeResult replay(List<StagedRecordEntity> versions, SurvivorshipConfig config,
                              String tenantId, String goldenRecordId, MergeEngine engine) {
        if (versions.isEmpty()) {
            return null;
        }
        MergeResult result = null;
        for (int i = 0; i < versions.size(); i++) {
            StagedRecordEntity src = versions.get(i);
            Map<String, Object> data = objectMapper.convertValue(src.getNormalizedData(), MAP_TYPE_REF);
            MergeRequest req = new MergeRequest(
                    i == 0 ? "create" : "update", data,
                    result != null ? result.goldenData() : null,
                    result != null ? result.fieldLineage() : null,
                    config, src.getSource(), src.getSourceRecordId(),
                    1.0,
                    src.getQualityScore() != null ? src.getQualityScore().doubleValue() : 0.8,
                    "re-survivorship-" + UUID.randomUUID(), goldenRecordId, tenantId,
                    null, null, null);
            result = engine.merge(req);
        }
        return result;
    }
}

package com.mdm.ingest.survivorship;

import com.fasterxml.jackson.databind.JsonNode;
import com.fasterxml.jackson.databind.ObjectMapper;
import com.mdm.core.domain.entity.GoldenRecordStatus;
import com.mdm.core.domain.membership.MembershipSpan;
import com.mdm.core.domain.membership.SourceRecordIdentity;
import com.mdm.core.domain.merge.MergeResult;
import com.mdm.core.domain.schema.SurvivorshipConfig;
import com.mdm.core.domain.stewardship.OverrideType;
import com.mdm.core.repository.SearchIndexRepository;
import com.mdm.core.repository.SourceMembershipRepository;
import com.mdm.ingest.blocking.MemberBlockingKeyGenerator;
import com.mdm.ingest.event.IngestEventEmitter;
import com.mdm.ingest.quality.LatestSourceReceivedAtResolver;
import com.mdm.ingest.quality.QualityScoreResolver;
import com.mdm.ingest.quality.QualityScoreResolver.QualityScoreInput;
import com.mdm.ingest.quality.QualityScoreResolver.QualityScoreResult;
import com.mdm.persistence.cache.GoldenRecordCacheEvictor;
import com.mdm.persistence.entity.FieldOverrideRuleEntity;
import com.mdm.persistence.entity.GoldenRecordEntity;
import com.mdm.persistence.entity.StagedRecordEntity;
import com.mdm.persistence.repository.FieldOverrideRuleJpaRepository;
import com.mdm.persistence.repository.GoldenRecordJpaRepository;
import com.mdm.persistence.repository.StagedRecordJpaRepository;
import io.micrometer.core.instrument.Metrics;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.stereotype.Component;
import org.springframework.transaction.annotation.Propagation;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.transaction.support.TransactionSynchronization;
import org.springframework.transaction.support.TransactionSynchronizationManager;

import java.math.BigDecimal;
import java.time.Instant;
import java.util.List;
import java.util.Objects;
import java.util.Optional;
import java.util.UUID;

/**
 * Regla de "la ficha que pierde un miembro" (WRK-SPEC-MDM-MEMBER-LOSS-001; RFC-PIPE-039). Toda operacion que cierra
 * un tramo de la xref en una ficha la invoca en su transaccion, con la ficha ya bloqueada ({@code FOR UPDATE}) y los
 * tramos ya cerrados:
 * <ul>
 *   <li>ficha inexistente o no activa: solo limpia sus claves ({@link Outcome#NOT_ACTIVE});</li>
 *   <li>sin miembros vigentes: pasa a {@code orphaned}, conserva {@code golden_data} como historico y pierde sus
 *       claves (DOM-MDM-SURVIVORSHIP-001 §2; {@link Outcome#ORPHANED});</li>
 *   <li>con miembros: desactiva los pins al registro que salio y re-ejecuta survivorship sobre todas las versiones de
 *       los miembros vigentes ({@link SurvivorshipReplay}); el linaje deja de nombrar al que salio
 *       ({@link Outcome#RECOMPUTED}, o {@link Outcome#NO_SOURCES} si ningun miembro tiene filas en Silver).</li>
 * </ul>
 * Los eventos se publican tras el commit.
 */
@Component
public class LosingGoldenRecordRecomputer {

    private static final Logger log = LoggerFactory.getLogger(LosingGoldenRecordRecomputer.class);

    public static final String DEACTIVATION_REASON = "auto_member_left";

    /**
     * @param departed           identidades cuyos tramos en la ficha se acaban de cerrar
     * @param survivorshipConfig reglas del {@code entity_type} de la ficha
     * @param actor              quien firma {@code updated_by} y las desactivaciones (p. ej. {@code pipeline:<run>})
     * @param evaluationInstant  instante de escritura y de evaluacion del quality score
     */
    public record LossContext(String tenantId, String goldenRecordId, List<SourceRecordIdentity> departed,
                              SurvivorshipConfig survivorshipConfig, String actor, Instant evaluationInstant) {}

    public enum Outcome { NOT_ACTIVE, ORPHANED, RECOMPUTED, NO_SOURCES }

    private final GoldenRecordJpaRepository goldenRecordRepository;
    private final StagedRecordJpaRepository stagedRecordRepository;
    private final SourceMembershipRepository membershipRepository;
    private final SearchIndexRepository searchIndex;
    private final MemberBlockingKeyGenerator memberKeyGenerator; // null sin generador
    private final FieldOverrideRuleJpaRepository overrideRepository;
    private final SurvivorshipReplay survivorshipReplay;
    private final LatestSourceReceivedAtResolver latestSourceReceivedAtResolver;
    private final QualityScoreResolver qualityScoreResolver;
    private final IngestEventEmitter eventEmitter;
    private final GoldenRecordCacheEvictor cacheEvictor;
    private final ObjectMapper objectMapper;

    public LosingGoldenRecordRecomputer(GoldenRecordJpaRepository goldenRecordRepository,
                                        StagedRecordJpaRepository stagedRecordRepository,
                                        SourceMembershipRepository membershipRepository,
                                        SearchIndexRepository searchIndex,
                                        Optional<MemberBlockingKeyGenerator> memberKeyGenerator,
                                        FieldOverrideRuleJpaRepository overrideRepository,
                                        SurvivorshipReplay survivorshipReplay,
                                        LatestSourceReceivedAtResolver latestSourceReceivedAtResolver,
                                        QualityScoreResolver qualityScoreResolver,
                                        IngestEventEmitter eventEmitter,
                                        GoldenRecordCacheEvictor cacheEvictor,
                                        ObjectMapper objectMapper) {
        this.goldenRecordRepository = goldenRecordRepository;
        this.stagedRecordRepository = stagedRecordRepository;
        this.membershipRepository = membershipRepository;
        this.searchIndex = searchIndex;
        this.memberKeyGenerator = memberKeyGenerator.orElse(null);
        this.overrideRepository = overrideRepository;
        this.survivorshipReplay = survivorshipReplay;
        this.latestSourceReceivedAtResolver = latestSourceReceivedAtResolver;
        this.qualityScoreResolver = qualityScoreResolver;
        this.eventEmitter = eventEmitter;
        this.cacheEvictor = cacheEvictor;
        this.objectMapper = objectMapper;
    }

    @Transactional(propagation = Propagation.MANDATORY)
    public Outcome recompute(LossContext loss) {
        String tenant = loss.tenantId();
        String grId = loss.goldenRecordId();
        cacheEvictor.evictAfterCommit(grId);
        List<SourceRecordIdentity> members = membershipRepository.findCurrentMembers(tenant, grId).stream()
                .map(MembershipSpan::identity).distinct().toList();
        Optional<GoldenRecordEntity> found = goldenRecordRepository.findByIdAndTenantId(UUID.fromString(grId), tenant);
        if (found.isEmpty() || !GoldenRecordStatus.ACTIVE.getValue().equalsIgnoreCase(found.get().getStatus())) {
            cleanUpKeys(tenant, grId, members);
            return Outcome.NOT_ACTIVE;
        }
        GoldenRecordEntity gr = found.get();
        String entityType = gr.getEntityType();
        deactivatePinsOfDeparted(gr, loss);
        gr.setSourceCount(members.size()); // mismo valor que refreshSourceCounts: un flush posterior no lo pisa
        gr.setUpdatedAt(loss.evaluationInstant());
        gr.setUpdatedBy(loss.actor());

        if (members.isEmpty()) {
            gr.setStatusEnum(GoldenRecordStatus.ORPHANED);
            goldenRecordRepository.saveAndFlush(gr);
            cleanUpKeys(tenant, grId, members);
            afterCommit(() -> eventEmitter.emitGoldenRecordMemberLeft(grId, entityType,
                    GoldenRecordStatus.ORPHANED.getValue(), tenant, loss.actor()));
            return Outcome.ORPHANED;
        }

        List<StagedRecordEntity> versions = stagedRecordRepository.findVersionsOfMembers(tenant, entityType,
                members.stream().map(SourceRecordIdentity::source).toArray(String[]::new),
                members.stream().map(SourceRecordIdentity::sourceRecordId).toArray(String[]::new));
        MergeResult result = survivorshipReplay.replay(versions, loss.survivorshipConfig(), tenant, grId);
        if (result == null) {
            log.warn("Golden record {} lost {} but none of its {} current members has rows in Silver; data kept",
                    grId, loss.departed(), members.size());
            goldenRecordRepository.saveAndFlush(gr);
            cleanUpKeys(tenant, grId, members);
            return Outcome.NO_SOURCES;
        }

        Instant latest = latestSourceReceivedAtResolver.resolve(
                versions.stream().map(StagedRecordEntity::getReceivedAt).toList());
        QualityScoreResult score = qualityScoreResolver.resolve(new QualityScoreInput(tenant, entityType,
                result.goldenData(), result.fieldLineage(), latest, loss.evaluationInstant()));
        JsonNode newData = objectMapper.valueToTree(result.goldenData());
        BigDecimal previousScore = gr.getQualityScore();
        boolean changed = !Objects.equals(gr.getGoldenData(), newData)
                || previousScore == null
                || previousScore.compareTo(BigDecimal.valueOf(score.score())) != 0;

        gr.setGoldenData(newData);
        gr.setFieldLineage(objectMapper.valueToTree(result.fieldLineage()));
        gr.setLatestSourceReceivedAt(latest);
        gr.setQualityScore(BigDecimal.valueOf(score.score()));
        goldenRecordRepository.saveAndFlush(gr);
        cleanUpKeys(tenant, grId, members);

        if (changed) {
            afterCommit(() -> eventEmitter.emitGoldenRecordMemberLeft(grId, entityType,
                    GoldenRecordStatus.ACTIVE.getValue(), tenant, loss.actor()));
        }
        maybeEmitQualityTierChange(previousScore, score, grId, entityType, loss);
        return Outcome.RECOMPUTED;
    }

    /** Misma regla que {@code StewardshipService.autoDeactivatePins}: identidad completa; pin legado, por id. */
    private void deactivatePinsOfDeparted(GoldenRecordEntity gr, LossContext loss) {
        for (FieldOverrideRuleEntity pin : overrideRepository.findByGoldenRecordIdAndTenantIdAndActiveAndOverrideType(
                gr.getId(), loss.tenantId(), true, OverrideType.SOURCE_PIN.name())) {
            if (loss.departed().stream().noneMatch(d -> pins(pin, d))) {
                continue;
            }
            pin.setActive(false);
            pin.setDeactivatedAt(loss.evaluationInstant());
            pin.setDeactivatedBy(loss.actor());
            pin.setDeactivationReason(DEACTIVATION_REASON);
            overrideRepository.saveAndFlush(pin);
            String field = pin.getField();
            String pinned = pin.getPinnedSourceRecordId();
            String grId = gr.getId().toString();
            String entityType = gr.getEntityType();
            afterCommit(() -> eventEmitter.emitFieldOverrideAutoDeactivated(grId, entityType, field,
                    OverrideType.SOURCE_PIN.name(), DEACTIVATION_REASON, null, pinned, null, null,
                    loss.tenantId()));
        }
    }

    private static boolean pins(FieldOverrideRuleEntity pin, SourceRecordIdentity departed) {
        return departed.sourceRecordId().equals(pin.getPinnedSourceRecordId())
                && (pin.getPinnedSource() == null || pin.getPinnedSource().equals(departed.source()));
    }

    /** Antes {@code PersistenceStepHandler.cleanUpAfterLosingMember}: repone las claves de los miembros y borra el resto. */
    private void cleanUpKeys(String tenant, String grId, List<SourceRecordIdentity> members) {
        if (memberKeyGenerator != null) {
            members.forEach(m -> memberKeyGenerator.ensureMemberKeys(m, grId));
        }
        searchIndex.deleteStaleEntries(tenant, grId, members);
    }

    /** DOM-MDM-SURVIVORSHIP-001 §3.7.3; ficha preexistente: sin score previo se compara con 0.5 (§3.3.6). */
    private void maybeEmitQualityTierChange(BigDecimal previousScore, QualityScoreResult score, String grId,
                                            String entityType, LossContext loss) {
        double previous = previousScore != null ? previousScore.doubleValue() : 0.5;
        String previousTier = qualityScoreResolver.tierFor(loss.tenantId(), entityType, previous);
        if (previousTier.equals(score.tier())) {
            return;
        }
        afterCommit(() -> eventEmitter.emitGoldenRecordQualityChanged(grId, entityType, previous, score.score(),
                previousTier, score.tier(), null, null, loss.tenantId(), loss.actor()));
        Metrics.counter("mdm_golden_record_quality_tier_changes_total",
                "entity_type", entityType, "from_tier", previousTier, "to_tier", score.tier()).increment();
    }

    private static void afterCommit(Runnable action) {
        if (TransactionSynchronizationManager.isSynchronizationActive()) {
            TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
                @Override public void afterCommit() { action.run(); }
            });
        } else {
            action.run();
        }
    }
}

        assertThat(status(l)).isEqualTo("active");
    }

    // AC8: mismos datos, pins y claves en T1 y T2; la ForceRule solo existe en T1. El recalculo de T1 no toca T2.
    @Test
    void recomputingInOneTenantLeavesTheOtherUntouched() throws Exception {
        String[] t1 = limaWithTwoMembersAndFoxtrot(T1);
        String[] t2 = limaWithTwoMembersAndFoxtrot(T2);
        String pin1 = insertSourcePin(T1, t1[0], "legal_name", "crm", "X1");
        String pin2 = insertSourcePin(T2, t2[0], "legal_name", "crm", "X1");
        JsonNode l2Data = goldenData(t2[0]);
        JsonNode l2Lineage = fieldLineage(t2[0]);
        List<Map<String, Object>> l2Keys = keysOfGoldenRecord(T2, t2[0]);

        insertForceRule(T1, "crm", "X1", t1[1]);
        moveX1(T1, t1[1]);

        assertThat(sourceCount(t2[0])).isEqualTo(2);
        assertThat(status(t2[0])).isEqualTo("active");
    }

    // AC9 (regresion): el unmerge ya recalculaba la ficha original; ninguna entrada de su linaje nombra al separado
    @Test
    void unmergeLeavesNoLineageToTheSeparatedRecord() throws Exception {

        fieldLineage(l).fields().forEachRemaining(e ->
                assertThat(e.getValue().path("source_record_id").asText()).as("record of %s", e.getKey())
                        .isNotEqualTo("X1"));
    }

# WRK-PLAN-MDM-MEMBER-DEPARTURE-001 — La ficha que pierde un miembro se recalcula

> **For agentic workers:** REQUIRED SUB-SKILL: Use kdd-superpowers:subagent-driven-development (recommended) or
> kdd-superpowers:executing-plans to implement this plan task-by-task. Each task is its own WRK-TASK file under
> `specs/work/`; steps use checkbox (`- [ ]`) syntax for tracking.

## Approach

**Goal:** que la ficha que pierde un miembro (cierre de su tramo en la xref) quede, en la misma transacción,
recalculada con survivorship sobre sus miembros restantes, podada si no se puede recalcular, u `orphaned` si se
queda sin miembros, y que su `field_lineage` deje de nombrar al registro que salió.

**Architecture:** puertos de lectura ampliados en `mdm-core` (versiones de miembros con `qualityScore`, superviviente
de merge manual, predicado pin ↔ identidad); en `mdm-ingest-service`, el encadenado de survivorship extraído
(`MemberSurvivorshipChain`, que `StewardshipService` pasa a usar sin cambiar resultados) y un recalculador puro
(`MemberDepartureRecalculator`) que decide el `outcome` y devuelve el resultado; los llamantes que ya escriben golden
records lo aplican: `PersistenceStepHandler.persistMembership` (movimiento por ForceRule) y
`StewardshipService.unmerge`/`unmergePreview`. Una guarda de arquitectura clasifica toda llamada que cierra tramos.

**Tech Stack:** Java 21, Spring Boot 3.4, Spring Data JPA, JUnit 5 + AssertJ + Mockito, Testcontainers.

**Spec:** `specs/work/WRK-SPEC-MDM-MEMBER-DEPARTURE-001-la-ficha-que-pierde-un-miembro-se-recalcula.md` — los
ejecutores leen la WRK-SPEC (sus *Constraints* y *Code Facts*) y su WRK-TASK antes de escribir código.

**Comandos** (desde `src/`; entorno: `export JAVA_HOME=~/jdk-21.0.2; export
PATH=$JAVA_HOME/bin:~/apache-maven-3.9.9/bin:$PATH; export DOCKER_API_VERSION=1.44`):

- Unitario: `mvn -q -pl <módulo> -am test -Dtest=<Clase> -Dsurefire.failIfNoSpecifiedTests=false`
- IT: `mvn -pl mdm-app -am verify -Dtest=NONE -Dsurefire.failIfNoSpecifiedTests=false -Dit.test=<ClaseIT>
  -Dfailsafe.failIfNoSpecifiedTests=false`

# WRK-SPEC-MDM-MEMBER-DEPARTURE-001 — La ficha que pierde un miembro se recalcula

Cierra RFC-PIPE-039 (OQ-4 de WRK-PLAN-MDM-SOURCE-IDENTITY-001). Cluster `work:manual-unification`.

## Problem Statement

Cuando un registro de origen sale de una ficha (se cierra su tramo vigente en `mdm_gold.source_record_xref`), la
ficha que lo pierde debe dejar de mostrar lo que aportaba ese registro. Hoy (verificado en el código, ver *Code
Facts*):

- **Movimiento del pipeline por ForceRule** (`membership_conflict`, WRK-SPEC-MDM-SOURCE-IDENTITY-001 §2, fila
  "F | L ≠ F"): se mueve el tramo, se limpian las claves y se recalcula `source_count` de L, pero **L no se escribe**:
  su `golden_data` y su `field_lineage` siguen mostrando los valores del registro que se fue y atribuyéndoselos; su
  versión no cambia, no se emite ningún evento para L y L puede quedarse `active` con cero miembros. Un consumidor
  puede leer en L un email o un NIF que ya vive en F.
- **Unmerge**: la ficha original ya se recalcula con survivorship sobre los miembros que quedan, **salvo** cuando
  ninguno de esos miembros tiene versiones localizables en Silver: entonces `golden_data` y `field_lineage` quedan
  intactos y siguen atribuyendo campos a los registros separados.
- **Resolución de un caso de revisión**: hoy no cierra tramos (ningún código de producción usa
  `review_resolution`); la cola de revisión es WRK-SPEC 3 (`work:review-queue`). Nada que corregir hoy, pero nada
  impide que el próximo camino que cierre tramos repita el defecto.
- **Absorción** (consolidación ADR-021, merge manual): la ficha que pierde todos sus miembros pasa a `merged` /
  `absorbed` y se conserva como está (lápida que redirige a la superviviente). No es el defecto del RFC.

- **Vista previa del unmerge**: con los restantes sin versiones en Silver anuncia `golden_data = {}` y el score
  actual (`StewardshipService.java:1507-1553`); debe anunciar lo mismo que escribirá el confirm.

## Proposed Change

### 1. Regla de dominio: "la ficha que pierde un miembro"

En la **misma transacción** que cierra el tramo de uno o varios registros D (los que salen) en una ficha L
(ADR-022 §2), L se resuelve así, en este orden de filas (gana la primera que aplica):

| Condición sobre L | `outcome` | Efecto sobre L |
|---|---|---|
| L no existe, o su `status` no es `active` (`merged`, `absorbed`, `deleted`, `orphaned`; un `status` nulo cuenta como `active`, mismo criterio que `isMissingOrOrphanUnderLock`) | `skipped_not_active` | Ninguno. Una absorbida conserva su último estado (DOM-MDM-SURVIVORSHIP-001 §3.2). |
| 0 miembros restantes | `orphaned` | `status = orphaned` (DOM-MDM-SURVIVORSHIP-001 §3.2). `golden_data`, `field_lineage`, `quality_score` y `latest_source_received_at` se conservan como lectura histórica; sus claves ya las borra la regla de claves existente. |
| Superviviente de un merge manual (regla `GOLDEN_TO_GOLDEN` activa con L como destino) y el llamante pide respetarla | `pruned` | Poda (abajo); `golden_data` no se recalcula, porque el recálculo completo "would discard the steward's decision" (409 de `/admin/re-survivorship`). |
| ≥ 1 miembro restante con ≥ 1 versión en Silver | `recomputed` | `golden_data` y `field_lineage` = encadenado de survivorship sobre las versiones de los miembros restantes (el mismo algoritmo y el mismo orden de entrada que `POST /admin/re-survivorship/{id}`). |
| ≥ 1 miembro restante, ninguno con versiones en Silver | `pruned` | Poda. |

- **Poda**: se elimina de `golden_data` y de `field_lineage` cada **clave de lineage** cuya entrada es de un registro
  de D (una clave de `golden_data` sin entrada de lineage se conserva). En las entradas que quedan se eliminan de
  `competing_values` las de D; si quedan menos de dos, `conflict = false` y `competing_values = null`. `previous`
  no se toca: no lleva `source_record_id` (DOM-MDM-SURVIVORSHIP-001 §3.6.1). Una entrada "es de" `(s, id)` si su
  `source_record_id = id`, su `source` es `s`, nulo o `"stewardship"` (pins legados) y su `rule_applied` no es
  `manual_override` (cuyo `source_record_id` es el operador).
- **Frescura y score** (`recomputed` y `pruned`): `latest_source_received_at = LatestSourceReceivedAtResolver.resolve`
  sobre los `received_at` de las versiones de los miembros restantes (nulo si no hay), nunca combinado con el valor
  persistido (DOM-MDM-SURVIVORSHIP-001 §3.7.1.1); `quality_score = QualityScoreResolver` sobre el resultado con el
  instante de evaluación que recibe el recálculo.
- **Pins a registros de D**: el recálculo **no los ve** — el encadenado usa un `DefaultMergeEngine` cuyo
  `FieldOverrideProvider` decora el real ocultando los `source_pin` activos que fijan un registro de D (el mismo
  patrón que los previews de override; los demás overrides, incluidos los `value_override`, se siguen aplicando). Si
  no hay tales pins se usa el bean inyectado. Así el resultado no depende del orden entre desactivar pins y
  recalcular, y la vista previa coincide con el confirm. En los caminos que escriben, esos pins se desactivan en la
  misma transacción (§10.9.4 p.2) y se emite `FieldOverrideAutoDeactivated` tras el commit. La coincidencia pin ↔
  registro es la actual: identidad completa si el pin tiene `pinned_source`, solo id si es legado (ADR-022 §6).
- **Escritura** (todo `outcome` salvo `skipped_not_active`): L ya está bloqueada `FOR UPDATE` por el camino que
  mueve el tramo; se escribe con `saveAndFlush` (`@Version` +1): un merge concurrente calculado sobre la versión
  anterior de L entra en conflicto (ADR-020). La escritura va **antes** del `refreshSourceCounts` nativo, que sigue
  siendo la última escritura de `source_count`.
- **Eventos y caché**:
  - Pipeline: se registran con `afterCommit` (patrón de `ConsolidationOverrideMigrator`) `golden_record.updated`
    para L con `{reason: "member_departure", outcome, departed: [{source, source_record_id}]}` (invalida L2 en los
    demás pods vía `CacheInvalidationListener`), `GoldenRecordQualityChanged` si el score de L cruza de tier
    (DOM-MDM-SURVIVORSHIP-001 §3.7.3) y los `FieldOverrideAutoDeactivated`; la caché local de L se evicta tras el
    commit (existente).
  - Unmerge: conserva sus eventos actuales, emitidos como hoy (`UnmergeExecuted`, `GoldenRecordUpdated` de la
    original, `GoldenRecordQualityChanged`, `FieldOverrideAutoDeactivated` síncronos; `golden_record.updated` de
    caché tras el commit). Cambiar su momento de emisión queda fuera de alcance.
- **Linaje**: en el pipeline, arista `PRODUCED` (run → L) con `{"action": "member_departure", "outcome": …}`
  (DOM-MDM-LINEAGE-001 §3.2.5, fila "Update de golden record"). El unmerge conserva sus aristas.
- **Fallos**: el recálculo no tiene degradación silenciosa: si lanza, la transacción entera se deshace y el camino
  falla como hoy (pipeline: reintentos de persistence y DLQ relanzable; unmerge: error de la operación). Un error de
  bloqueo durante el bloque de la ficha que pierde se traduce a `OptimisticLockingFailureException` (retroceso del
  orquestador), como los demás errores de bloqueo de la pertenencia.

### 2. Dónde vive

- **`MemberDepartureRecalculator`** (nuevo, `mdm-ingest-service`, paquete `com.mdm.ingest.membership`): cálculo
  puro, sin escrituras, solo con puertos de `mdm-core` (regla del proyecto "ZERO direct JPA imports outside
  mdm-persistence"). Entrada explícita: `tenantId`, `entityType`, `goldenRecordId`, `status`, `golden_data` y
  `field_lineage` actuales, `departed` (D), `remaining` (miembros restantes, que **da el llamante**: el pipeline los
  lee de la xref tras el `move`; el unmerge y su vista previa pasan la selección `remaining`), `SurvivorshipConfig`,
  `evaluationInstant` y `respectManualMerge`. Usa `SourceRecordVersionReader.findVersionsOfMembers` (nuevo),
  `FieldOverrideProvider.findActiveSourcePins`, `StewardshipRuleProvider.isManualMergeSurvivor` (nuevo, solo si
  `respectManualMerge`), `SurvivorshipRuleEvaluatorRegistry` + `MergeEngine` inyectado, `LatestSourceReceivedAtResolver`
  y `QualityScoreResolver`. Devuelve `outcome`, `golden_data`, `field_lineage`, `latest_source_received_at`,
  `QualityScoreResult` y los pins a desactivar.
- **`SourceRecordVersion`** gana `qualityScore` (nullable) y **`SourceRecordVersionReader`** gana
  `findVersionsOfMembers(tenantId, entityType, members)` sobre `StagedRecordJpaRepository.findVersionsOfMembers`
  (mismo orden); a diferencia de `findLatestVersion`, conserva `normalizedData` nulo como nulo, para que el
  encadenado reciba exactamente lo que recibe hoy.
- **`MemberSurvivorshipChain`** (nuevo, `mdm-ingest-service`): el encadenado create→update que hoy está en
  `StewardshipService.reSurvivorshipFromSources` (6 argumentos), sobre `SourceRecordVersion`, con los mismos
  parámetros (trust 1.0, quality de la versión o 0.8, run `re-survivorship-<uuid>`, `null` sin versiones).
  `StewardshipService` delega en él convirtiendo cada `StagedRecordEntity` sin alterar el orden que le pasa cada
  llamante (re-survivorship, overrides, `removeOverride`, unmerge, previews, corrección, vista previa del merge
  manual — esta última concatena por ficha y así sigue). `reSurvivorshipFromSourcesWithOverride` (vista previa de
  corrección) queda como está.
- **Predicado común pin ↔ identidad**: `SourceRecordIdentity.matchesPin(pinnedSource, pinnedSourceRecordId)` en
  `mdm-core`, usado por `autoDeactivatePins` y por el recalculador.
- **Llamantes**:
  - `PersistenceStepHandler.persistMembership`, en el bloque que mueve el tramo (`kind != null`), tras
    `cleanUpAfterLosingMember` y antes de `refreshSourceCounts`, con `respectManualMerge = true`, la configuración
    de `PipelineContext.getSurvivorshipConfig()` e `Instant.now()`. Cubre `force_rule` y, por la primera fila de la
    tabla, los movimientos desde absorbidas y huérfanas/borradas. La desactivación de pins va por
    `ConsolidationOverrideMigrator` (dueño de las escrituras de overrides del pipeline) con `deactivation_reason =
    auto_member_departed` y `deactivated_by = system:pipeline`. El output del paso `persistence` añade
    `member_departure: {golden_record_id, outcome}` cuando hubo movimiento.
  - `StewardshipService.unmerge`: el recálculo de la original se hace con el recalculador (`respectManualMerge =
    false`: el unmerge desactiva la regla `GOLDEN_TO_GOLDEN` de la original, comportamiento existente, y la
    original vuelve a ser elegible para re-survivorship); `autoDeactivatePins` pasa a ejecutarse antes del recálculo.
  - `StewardshipService.unmergePreview`: la vista de la original se calcula con el mismo recalculador y los mismos
    argumentos, sin escribir.
- **Guarda de llamadas** (`MemberDepartureGuardTest`, mdm-app): cuenta en el código de producción las llamadas a
  `.move(` y `.moveAllMembers(` sobre el puerto de pertenencia por fichero y las compara con una lista explícita
  (fichero, método del puerto, número, motivo): los `move` de `PersistenceStepHandler` y `StewardshipService`
  (pasan por el recalculador) y los `moveAllMembers` de consolidación y merge manual (exentos: la ficha que pierde
  queda absorbida). Una llamada nueva hace fallar el test hasta que alguien la clasifique; la futura resolución de
  revisión (WRK-SPEC 3) entra por ahí.

### 3. Alternativas consideradas

| Alternativa | Por qué no |
|---|---|
| A. Marcar L "pendiente de recálculo" y recalcular en un barrido asíncrono (el RFC lo admite) | Ventana en la que L sigue sirviendo datos ajenos, un proceso nuevo que operar y un estado que ninguna spec define. El recálculo síncrono cabe en la transacción: el movimiento por ForceRule es raro y L ya está bloqueada. |
| B. Poda siempre | Deja huecos que otro miembro vigente sí podría rellenar; no es "survivorship sobre los miembros vigentes". Se usa solo donde el recálculo no es posible (sin versiones) o no está permitido (superviviente de merge manual). |
| C. (elegida) Recálculo completo síncrono con el algoritmo de re-survivorship, poda como degradación, `orphaned` sin miembros | Cumple el valor esperado del RFC, DOM-MDM-PIPELINE-001 §10.6 p.3 y §10.8.4 p.3 y respeta la exclusión del merge manual; un solo algoritmo para todos los caminos. |

### 4. Recorrido por consumidores, bordes, concurrencia y fallos

- **Consumidores de L**: consulta del golden record y de su lineage (quedan sin D); caché L1/L2 (evento y evicción
  tras el commit); matching (L deja de ser candidata por las claves de D, ya hoy; si queda `orphaned`, sin claves);
  una ForceRule hacia L `orphaned` se ignora con warning y un tramo que apunte a L `orphaned` se mueve en la
  siguiente ingesta (`membership_orphan`) — ambos existentes; `/admin/re-survivorship` excluye no activas (L
  `orphaned`) y supervivientes de merge manual, como la tabla; `/sources` no cambia (historial por tramos).
- **Bordes**: valor que solo aportaba D → el campo desaparece si ningún restante lo aporta; `value_override` de L →
  se sigue aplicando; pin a D → oculto y desactivado; pin legado (sin fuente) cuyo id comparte un miembro restante de
  otra fuente → oculto también (el predicado legado casa por id) y desactivado, así que el campo nunca queda escrito
  por un pin inactivo; pin a un restante → gobierna su campo; unmerge → nunca `orphaned` (exige ≥ 1 restante).
- **Concurrencia**: el pipeline bloquea destino y L con `FOR UPDATE` en orden de id ascendente antes de escribir
  (`lockGoldenRecordsBeforeMove`) o, en el camino de respaldo, bloquea L después de escribir F (orden F → L,
  heredado). El recálculo lee miembros, versiones y pins bajo ese bloqueo. Un run concurrente sobre otro miembro de L
  que calculó su merge con la versión anterior falla la guarda de ADR-020 y se recalcula sin D. El unmerge ya
  bloquea la original. Los overrides de stewardship (`sourcePin`, `valueOverride`, `removeOverride`) escriben la
  fila del override y después L sin bloqueo previo, orden inverso al del pipeline: PostgreSQL puede abortar una de
  las dos por interbloqueo; en el pipeline se traduce a conflicto y reintento (§1 Fallos), en stewardship es el
  error de hoy. `POST /admin/re-survivorship/{id}` concurrente pierde por `@Version` y la ruta devuelve el error;
  en el lote cuenta como `failed`.
- **Fallos**: §1 *Fallos*. Un recálculo que falla siempre (p. ej. JSON de Silver corrupto) deja el run del
  registro que se mueve en DLQ y el registro sin mover: se prefiere fallar visible a mover dejando L con datos
  ajenos (mismo criterio de ADR-020: "fallar visible antes que perder datos").

## Acceptance Criteria

- [ ] AC1. Movimiento por ForceRule de R desde L (activa, no superviviente de merge manual, con otros miembros con
  versiones): tras el run, `golden_data` de L es igual al que produce después `POST /admin/re-survivorship/{L}`
  (que responde `unchanged` para `goldenData`), ninguna entrada de `field_lineage` de L tiene `(source,
  source_record_id)` de R como ganador ni en `competing_values`, ningún campo de L conserva un valor que solo
  aportaba R, y la `version` de L aumentó en 1.
- [ ] AC2. En ese movimiento, `latest_source_received_at` de L es el máximo `received_at` de las versiones de sus
  miembros restantes y `quality_score` de L es el de `QualityScoreResolver` sobre el resultado; si cruza de tier se
  publica `GoldenRecordQualityChanged` para L tras el commit.
- [ ] AC3. En ese movimiento se publica tras el commit un `golden_record.updated` para L con `reason:
  "member_departure"`, `outcome: "recomputed"` y `departed` con R; el output del paso `persistence` lleva
  `member_departure: {golden_record_id: L, outcome: "recomputed"}`; existe una arista `PRODUCED` run → L con
  `action = member_departure`; `source_count` de L es su número de tramos vigentes. Vale en modo síncrono y
  asíncrono.
- [ ] AC4. Un `source_pin` activo de L que fija R queda `active = false`, `deactivation_reason =
  auto_member_departed`, y se publica `FieldOverrideAutoDeactivated` tras el commit; un pin de L que fija otro
  miembro sigue activo y gobierna su campo; un `value_override` activo de L sigue aplicado. Un pin legado (sin
  fuente) al id de R, compartido por un miembro restante de otra fuente, queda desactivado y el campo de L no tiene
  `rule_applied = source_pin`.
- [ ] AC5. Si R era el único miembro de L: L queda `orphaned` con `golden_data` sin cambios, sin filas en
  `blocking_key_entries`, `source_count = 0`, `version` +1, y `outcome = "orphaned"` en el output y en el evento.
- [ ] AC6. Si la ficha del tramo que se cierra no existe o no está `active` (tramo hacia una absorbida o una borrada),
  no se escribe (`version` sin cambios) y el `outcome` es `skipped_not_active`.
- [ ] AC7. Si L es superviviente de un merge manual (regla `GOLDEN_TO_GOLDEN` activa), el pipeline poda: los campos
  cuyo ganador es R desaparecen de `golden_data` y `field_lineage`, el resto de `golden_data` queda igual y
  `outcome = "pruned"`.
- [ ] AC8. Unmerge cuyos restantes no tienen versiones en Silver: la original queda podada (campos de los separados
  fuera de `golden_data` y `field_lineage`, sin sus `competing_values`), y `POST /stewardship/unmerge/preview` con la
  misma selección devuelve exactamente ese `golden_data` y ese `field_lineage`. Con versiones, los resultados del
  unmerge, su vista previa, re-survivorship y previews de override son los de hoy (sus ITs y tests existentes en
  verde sin cambiar aserciones).
- [ ] AC9. Carrera: un run que re-ingesta otro miembro M de L y calculó su merge con la versión de L previa al
  movimiento termina con conflicto y reintento, y el `golden_data` final de L contiene la aportación de M y ninguna
  de R.
- [ ] AC10. Si el recálculo de L lanza, no queda nada escrito (tramo de R, claves, F, L, pins y `source_count` como
  antes del intento) y no se publica ningún evento de L ni de sus pins de ese intento.
- [ ] AC11. `MemberDepartureGuardTest` pasa sobre el código resultante y falla si se añade una llamada de producción
  a `move(` o `moveAllMembers(` del puerto de pertenencia no clasificada en su lista.
- [ ] AC12. Aislamiento por tenant: con datos idénticos en dos tenants, el recálculo de L en T1 no lee versiones,
  miembros, pins ni reglas de T2, y la ficha homóloga de T2 no cambia de versión.

## Open Questions

- OQ-1. DOM-MDM-PIPELINE-001 §10.8.4 p.3 dice que el GR origen que queda sin registros se marca `absorbed`;
  DOM-MDM-SURVIVORSHIP-001 §3.2 dice `orphaned` para el mismo caso ("via unmerge o source_to_golden"). El diseño
  sigue §3.2 (la spec dueña del ciclo de vida y el estado que el código ya trata como "sin miembros": F14). A decidir
  por el humano en consolidación; si gana §10.8.4, el cambio es `orphaned` → `absorbed` con arista `ABSORBED_INTO`
  L → F.
- OQ-2. El recálculo usa **todas** las versiones de cada miembro restante (como re-survivorship y el unmerge hoy),
  no solo la última: un valor que un miembro restante dejó de traer puede sobrevivir. Es RFC-PIPE-040.
- OQ-3. Una ficha `orphaned` conserva su `golden_data` y su `field_lineage` como lectura histórica (§3.2), así que su
  lineage sigue nombrando al registro que salió; y pierde sus claves en el acto (regla de claves de ADR-022), lo que
  hace inalcanzable la transición `orphaned → active` "si las blocking keys aún existen … durante un periodo de
  gracia" que §3.2 admite como posible. El evento `golden_record.updated` de L `orphaned` se emite aunque §3.2 diga
  "Propaga downstream: No", porque es la notificación del cambio de estado y la invalidación de caché (como la
  "notificación de absorción" de `absorbed`). A confirmar en consolidación.
- OQ-4 (a WRK-SPEC 3). La resolución de un caso de revisión que mueva un registro enlazado debe usar el
  recalculador; la guarda (AC11) lo fuerza.
- OQ-5. DOM-MDM-PIPELINE-001 §10.9.3 nota 4 nombra `loadSourcesForGoldenRecord` y `ORDER BY received_at,
  source_record_id`; el cargador real es `findVersionsOfMembers` con `coalesce(received_at, created_at),
  source_record_id, source, created_at` (F7). Corregir la nota en consolidación.

public class MemberDepartureRecalculator {

    public enum Outcome {
        RECOMPUTED("recomputed"), PRUNED("pruned"), ORPHANED("orphaned"), SKIPPED_NOT_ACTIVE("skipped_not_active");
        public String value();
    }

    /** remaining: miembros vigentes tras la salida (el llamante los da; ver WRK-SPEC §2). */
    public record Input(String tenantId, String entityType, String goldenRecordId, @Nullable String status,
                        Map<String, Object> goldenData, Map<String, FieldLineageEntry> fieldLineage,
                        List<SourceRecordIdentity> departed, List<SourceRecordIdentity> remaining,
                        @Nullable SurvivorshipConfig survivorshipConfig, Instant evaluationInstant,
                        boolean respectManualMerge) {}

    /**
     * goldenData/fieldLineage: lo que hay que escribir (RECOMPUTED, PRUNED) o lo actual (ORPHANED, SKIPPED).
     * latestSourceReceivedAt y quality: calculados en RECOMPUTED y PRUNED; null en ORPHANED y SKIPPED (no se tocan).
     * pinsToDeactivate: source_pins activos de la ficha que fijan un registro de departed (vacío en SKIPPED).
     */
    public record Result(Outcome outcome, Map<String, Object> goldenData, Map<String, FieldLineageEntry> fieldLineage,
                         @Nullable Instant latestSourceReceivedAt, @Nullable QualityScoreResult quality,
                         List<FieldOverrideRule> pinsToDeactivate) {

    }

                                       LatestSourceReceivedAtResolver latestSourceReceivedAtResolver,
                                       QualityScoreResolver qualityScoreResolver);

    public Result recalculate(Input in);

    /** Poda de WRK-SPEC §1 (package-private para tests). */
    static Pruned prune(Map<String, Object> goldenData, Map<String, FieldLineageEntry> lineage,
                        List<SourceRecordIdentity> departed);
    record Pruned(Map<String, Object> goldenData, Map<String, FieldLineageEntry> fieldLineage) {}
}

Algoritmo de `recalculate` (en este orden; primera fila que aplica):

1. `status` no nulo y distinto de `active` (ignorando mayúsculas) → `SKIPPED_NOT_ACTIVE`, entrada sin cambios, sin
   consultas.
2. `pinsToDeactivate` = `findActiveSourcePins(UUID.fromString(goldenRecordId), tenantId)` filtrados con
   `departed.anyMatch(d -> d.matchesPin(p.pinnedSource(), p.pinnedSourceRecordId()))` (vacío sin provider).
3. `remaining` vacía → `ORPHANED` (datos y lineage actuales, `latest`/`quality` nulos).
4. `respectManualMerge` y `ruleProvider.isManualMergeSurvivor(gr, tenant)` → `PRUNED` sobre los datos actuales.
5. `versions = versionReader.findVersionsOfMembers(tenant, entityType, remaining)`; vacía → `PRUNED`.
6. `RECOMPUTED`: `engine` = el bean si `pinsToDeactivate` está vacío; si no, `new DefaultMergeEngine(evaluatorRegistry,
   hiding(provider, pinIds))`, donde `hiding` delega en el provider real y quita de `findActiveOverrides` las
   entradas cuyo `id` está en `pinIds` y de `findActiveSourcePins` esas mismas reglas (patrón de
   `StewardshipService.overlayingOverrideProvider`, F6). `result = MemberSurvivorshipChain.merge(engine, versions →
   ChainInput(identity.source(), identity.sourceRecordId(), normalizedData, qualityScore), survivorshipConfig,
   tenant, gr)`.
7. En `PRUNED` y `RECOMPUTED`: `latest = latestSourceReceivedAtResolver.resolve(versions.receivedAt)` (lista vacía si

class MemberDepartureGuardTest {
    /** (fichero, método del puerto) → número de llamadas y motivo. Clasificar aquí toda llamada nueva. */
    private static final Map<String, Integer> ALLOWED = Map.of(
        "PersistenceStepHandler.java#move", 1,          // pasa por MemberDepartureRecalculator (004)
        "PersistenceStepHandler.java#moveAllMembers", 1, // consolidación: la que pierde queda merged (exenta)
        "StewardshipService.java#move", 1,               // unmerge: pasa por MemberDepartureRecalculator (006)
        "StewardshipService.java#moveAllMembers", 1);    // merge manual: la que pierde queda absorbed (exenta)
    private static final Pattern CALL = Pattern.compile("\\.(moveAllMembers|move)\\(");

    @Test void everySpanClosingCallIsClassified() throws IOException {
        Path root = Path.of("..").toAbsolutePath().normalize();                 // src/
        Map<String, Integer> found = new TreeMap<>();
        try (Stream<Path> files = Files.walk(root)) {
            files.filter(p -> p.toString().endsWith(".java") && p.toString().contains("/src/main/"))
                 .filter(p -> !p.getFileName().toString().equals("SourceMembershipRepositoryAdapter.java"))
                 .filter(p -> !p.getFileName().toString().equals("SourceMembershipRepository.java"))
                 .filter(p -> read(p).contains("SourceMembershipRepository"))   // solo quien usa el puerto
                 .forEach(p -> CALL.matcher(read(p)).results().forEach(m ->
                     found.merge(p.getFileName() + "#" + m.group(1), 1, Integer::sum)));
        }
        assertThat(found).as("AC11: clasificar cada llamada que cierra tramos (WRK-SPEC-MDM-MEMBER-DEPARTURE-001 §2)")
                         .isEqualTo(ALLOWED);
    }

    @Test void recalculatedPathsUseTheRecalculator() throws IOException {
        for (String f : List.of("PersistenceStepHandler.java", "StewardshipService.java")) {
            assertThat(read(find(f))).contains("MemberDepartureRecalculator");
        }
    }
}

# WRK-PLAN-MDM-MEMBER-LOSS-001 — La ficha que pierde un miembro se recalcula

> **For agentic workers:** REQUIRED SUB-SKILL: Use kdd-superpowers:subagent-driven-development (recommended) or kdd-superpowers:executing-plans to implement this plan task-by-task. Each task is its own WRK-TASK file under `specs/work/`; steps use checkbox (`- [ ]`) syntax for tracking.

## Approach

**Goal:** cuando el pipeline cierra el tramo de un registro X en una ficha activa L (ForceRule), L re-resuelve los
campos que ganaba X con survivorship sobre sus miembros vigentes (o pasa a `orphaned`), deja de nombrar a X en su
linaje y desactiva los pins sobre X — RFC-PIPE-039.

**Architecture:** el encadenado create→update de survivorship sobre miembros se extrae de `StewardshipService`
(`mdm-api-gateway`) a `MemberSurvivorship` (`mdm-ingest-service`) y stewardship delega en él. Un nuevo
`LosingMemberRecomputer` aplica la regla "ficha que pierde un miembro" campo a campo; `PersistenceStepHandler` lo
invoca en el único punto donde mueve un registro, dentro de la misma transacción y bajo el mismo `FOR UPDATE`.

**Tech Stack:** Java 21, Spring Boot 3.4, Spring Data JPA, JUnit 5 + AssertJ + Mockito, Testcontainers PostgreSQL
(`*IT.java`, failsafe). Build desde `src/`: `mvn -pl <módulo> -am test`, IT con `mvn -pl mdm-app -am verify -Dit.test=…`.

**Spec:** `specs/work/WRK-SPEC-MDM-MEMBER-LOSS-001-la-ficha-que-pierde-un-miembro-se-recalcula.md` — the plan argues
from the spec, so executors read both.

# WRK-SPEC-MDM-MEMBER-LOSS-001 — La ficha que pierde un miembro se recalcula

## Problem Statement

RFC-PIPE-039: cuando un registro de origen sale de un golden record (se cierra su tramo en
`mdm_gold.source_record_xref`), la ficha que lo pierde conserva en `golden_data` los valores que ganaba ese registro,
su `field_lineage` sigue nombrándolo, su quality score y `latest_source_received_at` siguen contándolo, sus
`source_pin` sobre él siguen activos y, si era el último miembro, la ficha sigue `active`. Un consumidor puede leer un
email o un NIF que ya vive en otra ficha.

Diagnóstico contra el código (HEAD `aacdae5`, Code Premises):

- **Unmerge ya cumple**: `StewardshipService.unmerge` recalcula la ficha original sobre los miembros que quedan
  (encadenado completo create→update, DOM-MDM-PIPELINE-001 §10.6 punto 3), reescribe `golden_data`, `field_lineage`,
  score y frescura, y desactiva los pins sobre los separados. La afirmación del RFC sobre el unmerge no se sostiene;
  solo se protege con un test de regresión.
- **El hueco está en el pipeline**: `PersistenceStepHandler.persistMembership`, tras `membershipRepository.move(...)`,
  solo limpia las blocking keys de la ficha que pierde (`cleanUpAfterLosingMember`) y difiere su evicción de caché.
  Es el único punto que saca un registro de una ficha activa fuera de stewardship: por una `ForceRule`
  `SOURCE_TO_GOLDEN`. Hoy ningún código de producción crea reglas `SOURCE_TO_GOLDEN` (solo `GOLDEN_TO_GOLDEN` en el
  merge manual); las que existen son legadas o migradas, y RFC-STEW-009 (mismo cluster) prevé crearlas. Este trabajo
  deja correcto ese punto para las reglas existentes y las futuras.
- **Resolución de revisión**: hoy no cierra ningún tramo (`REVIEW_RESOLUTION` sin llamadas de producción;
  `ReviewQueueService.resolve` solo actualiza el caso). Queda para cuando se cablee (Open Questions).

## Proposed Change

### Architecture

Al cerrar el tramo de un registro X en una ficha **activa** L, en la misma transacción y bajo el mismo `FOR UPDATE`,
L se corrige **campo a campo, solo en los campos afectados por X**: los campos cuyo linaje nombra a X se re-resuelven
con survivorship sobre las versiones en Silver de los miembros vigentes de L (o desaparecen si ninguno aporta valor);
el resto de campos no se toca. Si L se queda sin miembros pasa a `orphaned`.

El alcance por campo es deliberado: un recálculo completo de L re-derivaría desde los registros de origen campos que
una consolidación automática decidió entre fichas maestras (ADR-021 §1, "no se vuelve a los registros de origen") o
que un merge manual dejó a propósito (PROD-MDM-STEWARDSHIP-001, superviviente de merge manual excluido del
re-survivorship), y perdería campos de miembros sin versión en Silver (limitación de migración de ADR-022). Los
campos que X no ganaba no contienen nada de X.

Para que pipeline (`mdm-ingest-service`) y stewardship (`mdm-api-gateway`, que depende de ingest) compartan una única
implementación del encadenado de survivorship sobre miembros, este se extrae de `StewardshipService` a ingest. El
unmerge sigue haciendo su recálculo completo (§10.6 punto 3), sin cambio de comportamiento.

Alternativas descartadas: (A') recálculo completo de L — contradice ADR-021 §1 y la exclusión del superviviente de merge
manual; (B) marcar para recálculo y reconciliar — migración y ventana de lecturas obsoletas; (C) evento post-commit
que dispare el recálculo — los eventos son best-effort y el arreglo podría perderse.

### Components

1. **`MemberSurvivorship`** (`mdm-ingest-service`, paquete `com.mdm.ingest.survivorship`, `@Component`):
   - `List<StagedRecordEntity> loadCurrentMemberVersions(String tenantId, String entityType, String goldenRecordId)` —
     miembros vigentes de la xref (`findCurrentMembers`, identidades distintas) → `findVersionsOfMembers`.
   - `List<StagedRecordEntity> loadVersionsOfMembers(String tenantId, String entityType, List<SourceRecordIdentity> members)`.
   - `MergeResult fold(List<StagedRecordEntity> versions, SurvivorshipConfig config, String tenantId, String goldenRecordId, MergeEngine engine)`
     — el encadenado de la sobrecarga privada `StewardshipService.reSurvivorshipFromSources(…, MergeEngine)` (primera
     versión `create`, resto `update` sobre el acumulado), movido sin cambios; `null` si la lista está vacía.
   - En `StewardshipService` delegan en él exactamente: las dos sobrecargas de `reSurvivorshipFromSources`,
     `loadVersionsOfMembers` y `loadCurrentMemberVersions` (mismas firmas; la package-private sigue para sus tests).
     `reSurvivorshipFromSourcesWithOverride` y el resto de stewardship no cambian.
2. **`LosingMemberRecomputer`** (`mdm-ingest-service`, `com.mdm.ingest.pipeline.steps`, junto a
   `ConsolidationOverrideMigrator`): `Outcome recompute(PipelineContext ctx, String goldenRecordId, String destinationGoldenRecordId, SourceRecordIdentity departed)`.
   1. Relee la ficha con `findByIdForUpdate` (ya bloqueada en la transacción). Si no existe o su estado no es `active`
      → `SKIPPED`, sin escribir: absorbidas, `merged`, huérfanas y borradas quedan congeladas.
   2. Desactiva los `SOURCE_PIN` activos de la ficha que fijan `departed` (identidad completa; pin legado sin
      `pinned_source` casa solo por id, como `autoDeactivatePins`), con `deactivated_by = system:pipeline`,
      `deactivation_reason = auto_member_left`; tras el commit, `FieldOverrideAutoDeactivated` con
      `survivorGoldenRecordId = destinationGoldenRecordId` y el `pipeline_run_id` del contexto.
   3. Sin miembros vigentes → `status = orphaned`, `updated_at` = ahora; `golden_data` y `field_lineage` se conservan
      como instantánea histórica; no se emite `golden_record.updated` (orphaned no propaga downstream, §3.2). Reglas
      y overrides que apuntan a L se dejan como están: una ForceRule hacia una ficha `orphaned` "se ignora con
      warning" (DOM-MDM-PIPELINE-001 §10.8.5). → `ORPHANED`.
   4. **Campos afectados** = campos de `field_lineage` cuya entrada nombra a `departed`: `sourceRecordId` igual y
      (`source` igual o `source` nulo), o `departed` entre sus `competingValues` (mismo criterio); más los campos de los
      pins desactivados en el paso 2 (su linaje nombra a `stewardship`, no a la fuente de X, §10.9.6).
   5. `versions = loadCurrentMemberVersions(L)`; `result = fold(versions, ctx.getSurvivorshipConfig(), …, mergeEngine)`
      con el bean `MergeEngine` inyectado (respeta overrides activos); `result` es `null` si no hay versiones.
   6. Para cada campo afectado `f`: si `result` trae `f` → `golden_data[f] = result.goldenData[f]` y
      `field_lineage[f] = result.fieldLineage[f]` con `previous = FieldLineagePrevious.of(valor anterior de f, source
      anterior de f, ahora)` si el valor cambió (`null` si no, §3.6.1) y `resolvedAt = ahora`; si no → se quita `f` de `golden_data` y de `field_lineage`. Los
      campos no afectados conservan valor y entrada de linaje idénticos.
   7. `latest_source_received_at = LatestSourceReceivedAtResolver.resolve(receivedAt de versions)` (null sin versiones,
      como el unmerge); quality score = `QualityScoreResolver.resolve(...)` sobre el nuevo `golden_data`/`field_lineage`,
      con instante de evaluación `Instant.now()` (mismo criterio que `MergeStepHandler`).
   8. Si hubo campos afectados o cambió la frescura → `saveAndFlush` (sube `version`); `GoldenRecordQualityChanged` si
      cruza de tier. Si no → no escribe ni recalcula el score (`UNCHANGED`): un score que solo decae con el instante
      de evaluación no es un cambio de L (gate A2).
   9. Tras el commit, si algún valor cambió o desapareció: `golden_record.updated` de L con `version`, `fields_changed` (los
      afectados cuyo valor cambió o desapareció) y `previous_values` (sus valores anteriores) — nueva sobrecarga de
      `IngestEventEmitter.emitGoldenRecordUpdated` (DOM-MDM-LINEAGE-001 §3.1.2). → `RECOMPUTED`.
   10. Contador `mdm_golden_record_member_loss_total{entity_type, outcome}` con
       `outcome ∈ {recomputed, unchanged, orphaned, skipped}`.
3. **Enganche en `PersistenceStepHandler.persistMembership`**: en toda rama con `kind != null`, justo después de
   `move` + `cleanUpAfterLosingMember(previous)` y **antes** de `refreshSourceCounts`, llama a
   `losingMemberRecomputer.recompute(ctx, previous, grId, id)`. Se inyecta como `Optional<LosingMemberRecomputer>`
   (tests sin él siguen funcionando). El `saveAndFlush` del recálculo precede al `UPDATE` nativo de `source_count`,
   que sigue siendo la última escritura de esa columna. Hoy solo la rama `FORCE_RULE` llega con L activa; las ramas
   `CONSOLIDATION` y de huérfano llegan con L no activa y resultan `SKIPPED`.

### Data flow

ForceRule F mueve X de L a G: Match → `FORCED`; Merge escribe G; Persistence bloquea G y L (orden ascendente), escribe
G, cierra el tramo de X en L y lo abre en G (`force_rule`), limpia las claves de L, **re-resuelve los campos de L que
ganaba X (o deja L `orphaned`)**, recalcula `source_count` de G y L, commit. Tras el commit: evicción de L y G y, según
el caso, `golden_record.updated`, `GoldenRecordQualityChanged` y `FieldOverrideAutoDeactivated` de L.

### Error handling

Cualquier excepción del recálculo se propaga y revierte la transacción de persistencia completa (staged, golden, xref,
claves); aplica el reintento con backoff del orquestador y, agotado, la DLQ. No hay estado parcial; eventos y evicción
solo tras el commit. Riesgo aceptado: un defecto determinista al recalcular L (p. ej. una regla CEL que falla sobre una
versión antigua) deja la ingesta de X en DLQ hasta corregirlo; es el mismo contrato que un fallo del merge de G.

### Testing

  `LosingMemberRecomputerTest` (skip por estado; campos afectados por `source`/`sourceRecordId`, por pin legado y por

## Acceptance Criteria

Fixture de AC1–AC5 (`SourceIdentityPipelineIT`, schema `source-identity-supplier-schema.json`: `email` por
`source_priority` crm > erp_sap > web, el resto `most_recent`): X = (`crm`, `MX1`) con `legal_name`, `tax_id`, `phone`
y `email` = `x@lima.es`; después Y = (`erp_sap`, `MY1`) con el mismo `tax_id` (casa por `tax_id`), otro `legal_name` y
`email` = `y@lima.es`, sin `phone`. En L, X gana `email` (prioridad de fuente) y `phone` (único que lo aporta); Y gana
`legal_name` (más reciente, valor distinto). Una ForceRule `SOURCE_TO_GOLDEN` mueve X a otra ficha G en su siguiente ingesta.

- [ ] AC1. Tras el commit, `golden_data.email` de L es `y@lima.es`, `golden_data.phone` no existe y `legal_name` y
  `tax_id` tienen el valor de Y.
- [ ] AC2. Ninguna entrada de `field_lineage` de L tiene en su nivel superior (`source`, `sourceRecordId`) la identidad
  de X; `field_lineage.email` nombra a (`erp_sap`, `MY1`) y su `previous.value` es `x@lima.es`; toda entrada que
  antes del movimiento no nombraba a X (en el fixture, al menos `legal_name`) es idéntica (incluido `resolvedAt`).
- [ ] AC3. La `version` de L es mayor que antes del movimiento y su `quality_score` es el que devuelve
  `QualityScoreResolver` para el nuevo `golden_data`/`field_lineage`; `latest_source_received_at` se calcula sobre las
  versiones de los miembros vigentes (unitario: con un miembro restante más antiguo que X, pasa a su `received_at`).
- [ ] AC4. Un `source_pin` activo de L sobre X queda `active = false`, `deactivation_reason = auto_member_left`,
  `deactivated_by = system:pipeline`; un `value_override` activo de L sobre otro campo sigue activo y su valor sigue en
  `golden_data`.
- [ ] AC5. Variante con L = {X}: L pasa a `orphaned` (antes del cambio seguía `active`); su `golden_data` no cambia.
- [ ] AC6. Si la ficha del tramo cerrado no está `active` (absorbida/`merged`, huérfana, borrada, inexistente), no se
  escribe (versión sin cambios) — unitario sobre `LosingMemberRecomputer` e IT existente de consolidación en verde.
- [ ] AC7. Unitario: si `LosingMemberRecomputer.recompute` lanza, `PersistenceStepHandler.execute` propaga la excepción
  y no llama a `refreshSourceCounts`; la reversión la garantiza la transacción del orquestador (Code Premises).
- [ ] AC8. Tras el commit de AC1 se emite `golden_record.updated` de L con `version`, `fields_changed` = {`email`,
  `phone`} y `previous_values` = {`email`: `x@lima.es`, `phone`: el de X}; en AC5 no se emite; si la transacción
  revierte, no se emite nada (unitario sobre `LosingMemberRecomputer`).
- [ ] AC9. Unmerge (regresión, `StewardshipMembershipIT`): el `field_lineage` de la original no nombra en su nivel
  superior a ningún separado y su `golden_data` coincide con los valores del miembro restante del fixture.
- [ ] AC10. `StewardshipService` no contiene el bucle create→update: sus dos sobrecargas de
  `reSurvivorshipFromSources` delegan en `MemberSurvivorship.fold` (`reSurvivorshipFromSourcesWithOverride` fuera de
  alcance); `StewardshipServiceTest` y los IT de stewardship siguen en verde.

import com.fasterxml.jackson.core.type.TypeReference;

/**
 * Survivorship sobre los miembros vigentes de un golden record: lee de la xref sus miembros (ADR-022), carga de Silver
 * todas sus versiones en orden determinista y las encadena en el Merge Engine (primera {@code create}, resto
 * {@code update} sobre el acumulado). Compartido por stewardship (unmerge, re-survivorship, previews) y por el pipeline
 * (ficha que pierde un miembro, WRK-SPEC-MDM-MEMBER-LOSS-001). Movido sin cambios desde {@code StewardshipService}.
 *
 * @see <a href="specs/domain/DOM-MDM-SURVIVORSHIP-001-golden-record-survivorship.md">DOM-MDM-SURVIVORSHIP-001 §3.8.2</a>
 */
@Component
public class MemberSurvivorship {

    private static final TypeReference<Map<String, Object>> MAP_TYPE_REF = new TypeReference<>() {};

    private final SourceMembershipRepository membershipRepository;
    private final StagedRecordJpaRepository stagedRecordRepository;
    private final ObjectMapper objectMapper;

    public MemberSurvivorship(SourceMembershipRepository membershipRepository,
                              StagedRecordJpaRepository stagedRecordRepository, ObjectMapper objectMapper) {
        this.membershipRepository = membershipRepository;
        this.stagedRecordRepository = stagedRecordRepository;
        this.objectMapper = objectMapper;
    }

    /** Miembros vigentes (identidades distintas) de un golden record en la xref, dentro del tenant. */
    public List<SourceRecordIdentity> currentMembers(String tenantId, String goldenRecordId) {
        return membershipRepository.findCurrentMembers(tenantId, goldenRecordId).stream()
                .map(MembershipSpan::identity)
                .distinct()
                .toList();
    }

    /** Todas las versiones en Silver de los miembros vigentes, en el orden de {@link #loadVersionsOfMembers}. */
    public List<StagedRecordEntity> loadCurrentMemberVersions(String tenantId, String entityType, String goldenRecordId) {
        return loadVersionsOfMembers(tenantId, entityType, currentMembers(tenantId, goldenRecordId));
    }

    /**
     * Todas las versiones en Silver de los miembros dados, por identidad completa y en el orden determinista de
     * {@code StagedRecordJpaRepository#findVersionsOfMembers} (preview &equiv; confirm).
     */
    public List<StagedRecordEntity> loadVersionsOfMembers(String tenantId, String entityType,
                                                          List<SourceRecordIdentity> members) {
        if (members.isEmpty()) {
            return List.of();
        }
        String[] sources = members.stream().map(SourceRecordIdentity::source).toArray(String[]::new);
        String[] srids = members.stream().map(SourceRecordIdentity::sourceRecordId).toArray(String[]::new);
        return stagedRecordRepository.findVersionsOfMembers(tenantId, entityType, sources, srids);
    }

    /**
     * Encadena {@code versions} en {@code engine}: la primera en modo {@code create}, el resto en {@code update} sobre
     * el resultado acumulado. Usar siempre el bean {@code MergeEngine} de Spring (o uno que lo decore): uno propio
     * perderia los overrides activos del tenant.
     *
     * @return el resultado del ultimo merge, o {@code null} si no hay versiones
     */
    public MergeResult fold(List<StagedRecordEntity> versions, SurvivorshipConfig config, String tenantId,
                            String goldenRecordId, MergeEngine engine) {
        if (versions.isEmpty()) {
            return null;
        }
        StagedRecordEntity first = versions.getFirst();
        MergeResult result = engine.merge(new MergeRequest(
                "create", data(first), null, null,
                config, first.getSource(), first.getSourceRecordId(),
                1.0, quality(first),
                "re-survivorship-" + UUID.randomUUID(), goldenRecordId, tenantId,
                null, null, null));
        for (int i = 1; i < versions.size(); i++) {
            StagedRecordEntity src = versions.get(i);
            result = engine.merge(new MergeRequest(
                    "update", data(src), result.goldenData(), result.fieldLineage(),
                    config, src.getSource(), src.getSourceRecordId(),
                    1.0, quality(src),
                    "re-survivorship-" + UUID.randomUUID(), goldenRecordId, tenantId,
                    null, null, null));
        }
        return result;
    }

    private Map<String, Object> data(StagedRecordEntity e) {
        return objectMapper.convertValue(e.getNormalizedData(), MAP_TYPE_REF);
    }

    private static double quality(StagedRecordEntity e) {
        return e.getQualityScore() != null ? e.getQualityScore().doubleValue() : 0.8;
    }
}

# WRK-TASK-MDM-MEMBER-LOSS-001-002 — LosingMemberRecomputer

## Objective

Implementar la regla "ficha que pierde un miembro" de la WRK-SPEC (Components §2) como componente del pipeline:

1. Omite las fichas no activas.
2. Desactiva los pins sobre el registro que sale.
3. Deja la ficha `orphaned` si se queda sin miembros.
4. Si no, re-resuelve con `MemberSurvivorship.fold` **solo** los campos afectados, y recalcula el score y la frescura.
5. Emite tras el commit `golden_record.updated` con `version`, `fields_changed` y `previous_values`.

Esta tarea no engancha el componente al pipeline; eso lo hace la 003.

**Premises:**
- `ConsolidationOverrideMigrator.afterCommit` (`ConsolidationOverrideMigrator.java:85-93`) runs the action immediately when no synchronization is active. The helper here copies that behaviour, so unit tests without a transaction see the emissions straight away.
- `LatestSourceReceivedAtResolver.resolve` ignores nulls and returns null for an empty list (`LatestSourceReceivedAtResolver.java:47-52`).
- The lineage of a `SOURCE_PIN` records `sourceRecordId` = the pinned id and `source` = `pinnedSource` when the pin carries one, or `"stewardship"` for a legacy pin (`DefaultMergeEngine.java:141-145`, gate A2). A pin that carries a source is therefore already caught by the lineage predicate. A legacy pin is not, which is why the fields of the deactivated pins are added to the affected set.
- The score has a freshness term that decays with the evaluation instant (`GoldenQualityScoreCalculator.java:133-137`). A score that differs only because of that is **not** a reason to write: with nothing affected, L is written only if the freshness column changes (gate A2).

package com.mdm.ingest.pipeline.steps;

import com.fasterxml.jackson.core.type.TypeReference;
import com.fasterxml.jackson.databind.JsonNode;
import com.fasterxml.jackson.databind.ObjectMapper;
import com.mdm.core.domain.entity.GoldenRecordStatus;

import com.mdm.core.domain.merge.FieldLineageEntry.FieldLineagePrevious;

import com.mdm.persistence.entity.FieldOverrideRuleEntity;
import com.mdm.persistence.entity.GoldenRecordEntity;

import com.mdm.persistence.repository.FieldOverrideRuleJpaRepository;
import com.mdm.persistence.repository.GoldenRecordJpaRepository;
import io.micrometer.core.instrument.Metrics;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.stereotype.Component;
import org.springframework.transaction.support.TransactionSynchronization;
import org.springframework.transaction.support.TransactionSynchronizationManager;

import java.math.BigDecimal;
import java.time.Instant;
import java.util.ArrayList;
import java.util.HashMap;
import java.util.LinkedHashMap;
import java.util.LinkedHashSet;
import java.util.List;

/**
 * Regla de la "ficha que pierde un miembro" (WRK-SPEC-MDM-MEMBER-LOSS-001, RFC-PIPE-039). Al cerrarse en el pipeline el
 * tramo del registro {@code departed} en la ficha L (misma transaccion, L ya bloqueada {@code FOR UPDATE}):
 * <ol>
 *   <li>L no activa (absorbida, merged, huerfana, borrada) o inexistente: no se toca;</li>
 *   <li>se desactivan los {@code SOURCE_PIN} de L sobre {@code departed} (DOM-MDM-PIPELINE-001 §10.9.4 punto 2);</li>
 *   <li>sin miembros vigentes: L pasa a {@code orphaned} con sus datos como instantanea historica y sin propagar
 *       (DOM-MDM-SURVIVORSHIP-001 §3.2);</li>
 *   <li>si no, solo los campos cuyo linaje nombra a {@code departed} (o de un pin desactivado) se re-resuelven con
 *       survivorship sobre las versiones de los miembros vigentes; el resto no se toca (ADR-021 §1, superviviente de
 *       merge manual). Score y frescura se recalculan sobre el resultado.</li>
 * </ol>
 * Eventos solo tras el commit.
 */
@Component
public class LosingMemberRecomputer {

    private static final Logger log = LoggerFactory.getLogger(LosingMemberRecomputer.class);
    private static final TypeReference<Map<String, Object>> MAP_TYPE_REF = new TypeReference<>() {};
    static final String DEACTIVATION_REASON = "auto_member_left";
    static final String DEACTIVATED_BY = "system:pipeline";

    /** Resultado del recalculo, tambien etiqueta {@code outcome} de {@code mdm_golden_record_member_loss_total}. */
    public enum Outcome { RECOMPUTED, UNCHANGED, ORPHANED, SKIPPED }

    private final GoldenRecordJpaRepository goldenRecordRepository;
    private final FieldOverrideRuleJpaRepository overrideRepository;
    private final MemberSurvivorship memberSurvivorship;
    private final MergeEngine mergeEngine;
    private final QualityScoreResolver qualityScoreResolver;
    private final LatestSourceReceivedAtResolver latestSourceReceivedAtResolver;
    private final IngestEventEmitter eventEmitter;
    private final ObjectMapper objectMapper;

    public LosingMemberRecomputer(GoldenRecordJpaRepository goldenRecordRepository,
                                  FieldOverrideRuleJpaRepository overrideRepository,
                                  MemberSurvivorship memberSurvivorship, MergeEngine mergeEngine,
                                  QualityScoreResolver qualityScoreResolver,
                                  LatestSourceReceivedAtResolver latestSourceReceivedAtResolver,
                                  IngestEventEmitter eventEmitter, ObjectMapper objectMapper) {
        this.goldenRecordRepository = goldenRecordRepository;
        this.overrideRepository = overrideRepository;
        this.memberSurvivorship = memberSurvivorship;
        this.mergeEngine = mergeEngine;
        this.qualityScoreResolver = qualityScoreResolver;
        this.latestSourceReceivedAtResolver = latestSourceReceivedAtResolver;
        this.eventEmitter = eventEmitter;
        this.objectMapper = objectMapper;
    }

    /**
     * @param goldenRecordId            ficha que pierde el miembro (L)
     * @param destinationGoldenRecordId ficha a la que se movio (para el evento de pin desactivado)
     * @param departed                  identidad completa del registro que salio
     */
    public Outcome recompute(PipelineContext ctx, String goldenRecordId, String destinationGoldenRecordId,
                             SourceRecordIdentity departed) {
        Optional<GoldenRecordEntity> row = goldenRecordRepository.findByIdForUpdate(UUID.fromString(goldenRecordId));
        if (row == null || row.isEmpty() || !isActive(row.get())) {
            return count(ctx, Outcome.SKIPPED);
        }
        GoldenRecordEntity gr = row.get();
        String tenant = ctx.getTenantId();
        Instant now = Instant.now();
        Set<String> pinnedFields = deactivatePinsOn(gr, departed, destinationGoldenRecordId, ctx, now);

        if (memberSurvivorship.currentMembers(tenant, goldenRecordId).isEmpty()) {
            gr.setStatusEnum(GoldenRecordStatus.ORPHANED);
            gr.setUpdatedAt(now);
            goldenRecordRepository.saveAndFlush(gr);
            log.info("Golden record {} lost its last member {}; now orphaned", goldenRecordId, departed.display());
            return count(ctx, Outcome.ORPHANED);
        }

        Map<String, Object> data = gr.getGoldenData() != null
                ? new LinkedHashMap<>(objectMapper.convertValue(gr.getGoldenData(), MAP_TYPE_REF))
                : new LinkedHashMap<>();
        Map<String, FieldLineageEntry> lineage = readLineage(gr.getFieldLineage(), goldenRecordId);
        Set<String> affected = new LinkedHashSet<>();
        lineage.forEach((field, e) -> { if (names(e, departed)) affected.add(field); });
        pinnedFields.stream().filter(lineage::containsKey).forEach(affected::add);

        List<StagedRecordEntity> versions = memberSurvivorship.loadCurrentMemberVersions(tenant, gr.getEntityType(),
                goldenRecordId);
        MergeResult folded = affected.isEmpty() ? null
                : memberSurvivorship.fold(versions, ctx.getSurvivorshipConfig(), tenant, goldenRecordId, mergeEngine);

        List<String> fieldsChanged = new ArrayList<>();
        Map<String, Object> previousValues = new HashMap<>();
        for (String field : affected) {
            FieldLineageEntry old = lineage.get(field);
            Object oldValue = data.get(field);
            FieldLineageEntry fresh = folded != null ? folded.fieldLineage().get(field) : null;
            if (fresh != null && folded.goldenData().containsKey(field)) {
                Object value = folded.goldenData().get(field);
                boolean changed = !sameValue(value, oldValue);
                data.put(field, value);
                // DOM-MDM-SURVIVORSHIP-001 §3.6.1: previous = null si el valor no cambio
                lineage.put(field, FieldLineageEntry.of(value, fresh.source(), fresh.sourceRecordId(),
                        fresh.ruleApplied(), now, fresh.confidence(), fresh.conflict(), fresh.competingValues(),
                        changed ? FieldLineagePrevious.of(oldValue, old.source(), now) : null));
                if (changed) {
                    fieldsChanged.add(field);
                    previousValues.put(field, oldValue);
                }
            } else {
                data.remove(field);
                lineage.remove(field);
                fieldsChanged.add(field);
                previousValues.put(field, oldValue);
            }
        }

        Instant latest = latestSourceReceivedAtResolver.resolve(
                versions.stream().map(StagedRecordEntity::getReceivedAt).toList());
        boolean freshnessChanged = !Objects.equals(latest, gr.getLatestSourceReceivedAt());
        // Sin campos afectados solo la frescura justifica escribir (§3.8.2 2e y su excepcion de frescura): un score
        // que solo decae con el instante de evaluacion no es un cambio de L
        if (affected.isEmpty() && !freshnessChanged) {
            return count(ctx, Outcome.UNCHANGED);
        }
        QualityScoreResult score = qualityScoreResolver.resolve(new QualityScoreInput(tenant, gr.getEntityType(),
                data, lineage, latest, now));
        BigDecimal previousScore = gr.getQualityScore();

        gr.setGoldenData(objectMapper.valueToTree(data));
        gr.setFieldLineage(objectMapper.valueToTree(lineage));
        gr.setLatestSourceReceivedAt(latest);
        gr.setQualityScore(BigDecimal.valueOf(score.score()));
        gr.setUpdatedAt(now);
        GoldenRecordEntity saved = goldenRecordRepository.saveAndFlush(gr);
        maybeEmitTierChange(previousScore, score, goldenRecordId, gr.getEntityType(), ctx);
        if (!fieldsChanged.isEmpty()) { // sin valores cambiados no hay nada que propagar (§3.8.2 2e)
            int version = saved.getVersion();
            List<String> changed = List.copyOf(fieldsChanged);
            afterCommit(() -> eventEmitter.emitGoldenRecordUpdated(goldenRecordId, gr.getEntityType(), version,
                    changed, previousValues, ctx.getSource(), tenant, ctx.getUserId()));
        }
        return count(ctx, Outcome.RECOMPUTED);
    }

    private static boolean isActive(GoldenRecordEntity gr) {
        return gr.getStatus() == null || GoldenRecordStatus.ACTIVE.getValue().equalsIgnoreCase(gr.getStatus());
    }

    /** La entrada nombra al registro: identidad completa, o solo id si la entrada no trae fuente (legado). */
    private static boolean names(FieldLineageEntry e, SourceRecordIdentity id) {
        if (sameRecord(e.source(), e.sourceRecordId(), id)) return true;
        return e.competingValues() != null && e.competingValues().stream()
                .anyMatch(c -> sameRecord(c.source(), c.sourceRecordId(), id));
    }

    private static boolean sameRecord(String source, String sourceRecordId, SourceRecordIdentity id) {
        return id.sourceRecordId().equals(sourceRecordId) && (source == null || id.source().equals(source));
    }

    private boolean sameValue(Object a, Object b) {
        return Objects.equals(objectMapper.valueToTree(a), objectMapper.valueToTree(b));
    }

    /** Linaje campo a campo: una entrada ilegible se conserva tal cual y no cuenta como afectada. */
    private Map<String, FieldLineageEntry> readLineage(JsonNode node, String goldenRecordId) {
        Map<String, FieldLineageEntry> out = new LinkedHashMap<>();
        if (node == null || !node.isObject()) return out;
        node.fields().forEachRemaining(e -> {
            try {
                out.put(e.getKey(), objectMapper.treeToValue(e.getValue(), FieldLineageEntry.class));
            } catch (Exception ex) {
                log.warn("Unreadable lineage entry {} of golden record {}: {}", e.getKey(), goldenRecordId,
                        ex.getMessage());
            }
        });
        return out;
    }

    /** Desactiva los SOURCE_PIN de L sobre {@code departed}; devuelve sus campos. */
    private Set<String> deactivatePinsOn(GoldenRecordEntity gr, SourceRecordIdentity departed, String destination,
                                         PipelineContext ctx, Instant now) {
        Set<String> fields = new LinkedHashSet<>();
        for (FieldOverrideRuleEntity pin : overrideRepository.findByGoldenRecordIdAndTenantIdAndActiveAndOverrideType(
                gr.getId(), ctx.getTenantId(), true, "SOURCE_PIN")) {
            if (pin.getPinnedSourceRecordId() == null
                    || !sameRecord(pin.getPinnedSource(), pin.getPinnedSourceRecordId(), departed)) {
                continue;
            }
            pin.setActive(false);
            pin.setDeactivatedAt(now);
            pin.setDeactivatedBy(DEACTIVATED_BY);
            pin.setDeactivationReason(DEACTIVATION_REASON);
            overrideRepository.saveAndFlush(pin); // el FieldOverrideProvider del fold lo lee por consulta
            fields.add(pin.getField());
            String grId = gr.getId().toString();
            String field = pin.getField();
            String pinned = pin.getPinnedSourceRecordId();
            afterCommit(() -> eventEmitter.emitFieldOverrideAutoDeactivated(grId, gr.getEntityType(), field,
                    "SOURCE_PIN", DEACTIVATION_REASON, destination, pinned, ctx.getPipelineRunId(),
                    ctx.getSource(), ctx.getTenantId()));
        }
        return fields;
    }

    private void maybeEmitTierChange(BigDecimal previousScore, QualityScoreResult score, String grId,
                                     String entityType, PipelineContext ctx) {
        double previous = previousScore != null ? previousScore.doubleValue() : 0.5;
        String previousTier = qualityScoreResolver.tierFor(ctx.getTenantId(), entityType, previous);
        if (previousTier.equals(score.tier())) return;
        afterCommit(() -> eventEmitter.emitGoldenRecordQualityChanged(grId, entityType, previous, score.score(),
                previousTier, score.tier(), ctx.getPipelineRunId(), ctx.getSource(), ctx.getTenantId(),
                ctx.getUserId()));
    }

    private static Outcome count(PipelineContext ctx, Outcome outcome) {
        Metrics.counter("mdm_golden_record_member_loss_total",
                "entity_type", ctx.getEntityType(), "outcome", outcome.name().toLowerCase()).increment();
        return outcome;
    }

    private static void afterCommit(Runnable action) {
        if (TransactionSynchronizationManager.isSynchronizationActive()) {
            TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
                @Override public void afterCommit() { action.run(); }
            });
        } else {
            action.run();
        }
    }
}

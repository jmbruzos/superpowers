# WRK-PLAN-MDM-MEMBER-EXIT-001 — La ficha que pierde un miembro se recalcula

> **For agentic workers:** REQUIRED SUB-SKILL: Use kdd-superpowers:subagent-driven-development (recommended) or kdd-superpowers:executing-plans to implement this plan task-by-task. Each task is its own WRK-TASK file under `specs/work/`; steps use checkbox (`- [ ]`) syntax for tracking.

## Approach

**Goal:** que la ficha que pierde un miembro por una ForceRule (o por un unmerge sin versiones en Silver) deje de
mostrar y de atribuir en su linaje lo que aportaba ese registro, y que pase a `orphaned` si se queda sin miembros.

**Architecture:** un calculador puro (`MemberSurvivorshipRecalculator`) repite el encadenado create→update de
`StewardshipService.reSurvivorshipFromSources` sobre las versiones en Silver de los miembros vigentes, leídas por un
puerto nuevo (`SourceRecordVersionReader.findVersionsOfMembers`). Un aplicador puro (`MemberExitApplier`) decide qué
se escribe: completo, parcial (superviviente protegida de un merge manual) o retirada de respaldo, con `previous` en
los campos que cambian. `PersistenceStepHandler.persistMembership` lo invoca dentro de la transacción del movimiento,
con la ficha bloqueada; los emisores post-commit publican `golden_record.updated` para ella.

**Tech Stack:** Java 21, Spring Boot 3.4, Spring Data JPA, JUnit 5 + AssertJ + Mockito, Testcontainers PostgreSQL
(`*IT.java`, failsafe). Maven desde `src/`.

**Spec:** `specs/work/WRK-SPEC-MDM-MEMBER-EXIT-001-la-ficha-que-pierde-un-miembro-se-recalcula.md` — el plan argumenta
desde la spec; quien ejecute lee las dos.

**Comandos** (desde `src/`):

# WRK-SPEC-MDM-MEMBER-EXIT-001 — La ficha que pierde un miembro se recalcula

Activa RFC-PIPE-039. Cluster `work:manual-unification` (ADR-011/ADR-012), independiente de la reescritura del merge
manual (RFC-STEW-007, RFC-STEW-009): no toca la ficha que **gana** miembros.

## Problem Statement

Cuando un registro de origen sale de una ficha (se cierra su tramo en `mdm_gold.source_record_xref`), sus blocking
keys se retiran y `source_count` baja, pero la ficha que lo pierde puede seguir mostrando en `golden_data`,
`field_lineage` y `quality_score` lo que aportaba ese registro (RFC-PIPE-039). Un consumidor lee un email o un NIF que
ya vive en otra ficha, `/golden-records/{id}/lineage` atribuye campos a un registro que no le pertenece, y el match
sigue comparando registros entrantes contra esos valores, porque los comparadores leen el `golden_data` de la ficha
candidata (FRAG-MDM-MATCH-001, `DefaultMatchEngine.java:179,195`).

Estado real por cada operación que cierra tramos (verificado, ver Code Premises):

| Operación que cierra el tramo | Ficha que pierde el miembro | Hoy |
|---|---|---|
| ForceRule que mueve un registro enlazado (`force_rule`), también cuando el merge siguió `ABSORBED_INTO` | Sigue `active` | **No se recalcula** (solo claves y `source_count`); sin evento; los `source_pin` al registro que salió siguen activos. Si era su único miembro, queda `active` con `source_count = 0` |
| Unmerge (`unmerge`) | Sigue `active` | Se recalcula con `reSurvivorshipFromSources(remainingStaged)`; **pero si devuelve `null`** (miembros restantes sin versión en Silver) conserva `golden_data`/`field_lineage` previos |
| Tramo legado de ficha absorbida (`consolidation`), tramo a ficha inexistente/borrada/huérfana (`pipeline_run`), consolidación automática, merge manual | No activa (`merged`/`absorbed`/`orphaned`/inexistente) | Nada que recalcular |
| Resolución de revisión (`review_resolution`) | — | Valor del enum sin escritor en producción |

## Proposed Change

**Regla.** Tras cerrar el tramo de un miembro por ForceRule o por unmerge, si la ficha que lo pierde sigue `active`,
en la **misma transacción** que el cierre: (a) si le quedan miembros vigentes, se recalcula con survivorship sobre
ellos (`golden_data`, `field_lineage`, `quality_score`, `latest_source_received_at`) — **parcialmente** si es la
superviviente protegida de un merge manual (abajo); (b) si no le queda ninguno, pasa a `orphaned`. El calculador queda
disponible para otros cierres (p. ej. la resolución de revisión), pero conectarlos no forma parte de este trabajo.

### Architecture

- **`MemberSurvivorshipRecalculator`** (nuevo, `mdm-ingest-service`, paquete `com.mdm.ingest.survivorship`):
  calculador puro sobre puertos de `mdm-core`. Entrada: tenant, id de la ficha, `entity_type`, `SurvivorshipConfig`,
  la lista de versiones de los miembros vigentes y el `MergeEngine` a usar. Salida: `Recomputation{goldenData,
  fieldLineage, qualityScore, latestSourceReceivedAt}`, o `null` si la lista está vacía. Ejecuta **exactamente** el
  encadenado actual de `StewardshipService.reSurvivorshipFromSources` (primera versión `create`, el resto `update`,
  mismos `trustScore` 1.0 y `qualityScore` de staged con fallback 0.8) y pide la nota a `QualityScoreResolver` con el
  candidato de frescura de `LatestSourceReceivedAtResolver` sobre esas versiones y `evaluationInstant = Instant.now()`
  en el momento del recálculo (mismo criterio que `MergeStepHandler.java:258` y `/admin/re-survivorship`).
- **`StewardshipService` no se refactoriza**: `reSurvivorshipFromSources`, los previews y `/admin/re-survivorship`
  siguen como están. La equivalencia la fija un test de paridad del calculador **contra** `reSurvivorshipFromSources`
  (dos implementaciones, un test que las ata; AC9).
- **Superviviente protegida de un merge manual** (ficha con `ForceRule{GOLDEN_TO_GOLDEN, active}` cuyo
  `goldenRecordId` es ella; PROD-MDM-STEWARDSHIP-001 §3.8.5 la excluye de re-survivorship): **recálculo parcial**.
  Se calcula el resultado completo sobre los miembros vigentes pero solo se aplican los campos cuya entrada de
  linaje apunta al registro que salió: cada uno toma el valor y la entrada del recálculo, o desaparece si el recálculo
  no lo produce. El resto de campos no se toca.
- **`previous` del linaje**: tras un recálculo (completo o parcial), cada campo cuyo valor cambia respecto al
  `golden_data` anterior lleva `previous = {value, source, changed_at, changed_by_pipeline_run}` con el valor y el
  `source` anteriores (DOM-MDM-SURVIVORSHIP-001 §3.6.1: "Valor anterior si hubo cambio"); un campo que desaparece no
  deja entrada. Lo escribe el aplicador, no el calculador.
- **Lectura de versiones por puerto**: `SourceRecordVersionReader.findVersionsOfMembers(tenantId, entityType,
  List<SourceRecordIdentity>)` en `mdm-core`, implementado en `mdm-persistence` sobre la consulta existente
  `StagedRecordJpaRepository.findVersionsOfMembers` (mismo orden: `coalesce(received_at, created_at)`,
  `source_record_id`, `source`, `created_at` ascendentes). `SourceRecordVersion` gana `qualityScore` (nullable). El
  código nuevo no importa JPA fuera de `mdm-persistence`.
- **Aplicación del resultado**: la hace quien ya tiene la entidad bloqueada — `PersistenceStepHandler` en el
  pipeline, `StewardshipService` en el unmerge.

### Data flow

**Pipeline — movimiento por ForceRule** (`persistMembership`, rama `kind != null`, con `previous` ya bloqueado
`FOR UPDATE`). Tras `move` y `cleanUpAfterLosingMember(previous)`:

1. Se lee la fila bloqueada de `previous`. Si no es `active`, termina aquí (comportamiento de hoy: las ramas
   `consolidation` y `pipeline_run` nunca dejan una ficha activa).
2. `MemberExitPinDeactivator`: desactiva cada `source_pin` activo de `previous` cuyo registro fijado es la identidad
   que salió (identidad completa; un pin legado sin `pinned_source` casa por id), con `deactivation_reason =
   member_exit`, `deactivated_by = system:pipeline`; publica `FieldOverrideAutoDeactivated` tras el commit (mismo
   patrón que `ConsolidationOverrideMigrator`). DOM-MDM-PIPELINE-001 §10.9.4 p.2.
3. Miembros vigentes de `previous` desde la xref (el `move` ya cerró el tramo).
   - **Cero miembros** → `status = orphaned` (DOM-MDM-SURVIVORSHIP-001 §3.2), `updated_at`, `saveAndFlush`. Todas
     las demás columnas (`golden_data`, `field_lineage`, `quality_score`, `latest_source_received_at`) se conservan
     como instantánea histórica de solo lectura: el registro que salió fue de verdad su último aportador. Sus claves
     ya las borró `cleanUpAfterLosingMember`. Overrides y reglas que apunten a la ficha no se tocan (OQ-4).
   - **Uno o más** → `findVersionsOfMembers` + calculador con la `SurvivorshipConfig` del contexto (schema activo del
     mismo `entity_type`). Resultado no nulo → aplicación completa (o parcial si es superviviente protegida) de
     `golden_data`, `field_lineage` (con `previous`), `quality_score`, `latest_source_received_at`, `updated_at` y
     `saveAndFlush` (el `@Version` sube). En la aplicación parcial, `quality_score` se recalcula con el resolver sobre
     el `golden_data`/`field_lineage` resultantes. Resultado nulo → **retirada de respaldo** (abajo).
4. `previous` se añade a `memberExitGoldenRecords`; si hubo recálculo se invoca la sobrecarga de
   `maybeEmitQualityTierChange` con la nota anterior de `previous` y su nuevo `QualityScoreResult`.
   `cacheEvictor.evictAfterCommit(previous)` se mantiene.
5. Tras el commit, `IngestService` (ingesta síncrona) y `AsyncPipelineExecutor` (asíncrona) emiten
   `golden_record.updated` para cada ficha de `memberExitGoldenRecords` (invalidación de caché en los demás pods,
   ARCH-MDM-PERFORMANCE-001 §3.3.1, y propagación downstream). Un reintento empieza con la lista vacía
   (`clearMergeOutput`), así que un intento revertido no deja eventos.

**Unmerge**: sin cambio de flujo. Si `reSurvivorshipFromSources(remainingStaged)` devuelve `null`, se aplica la
retirada de respaldo con las identidades separadas en lugar de conservar las columnas previas. La validación del
unmerge ya impide dejar la ficha sin miembros, así que el unmerge nunca orfana.

**Retirada de respaldo** (miembros vigentes sin ninguna versión en Silver; defensivo, no debería ocurrir tras la
migración V38): se eliminan de `golden_data` y de `field_lineage` los campos cuya entrada de linaje apunta a la
identidad que salió (`source` + `source_record_id`; entrada legada sin `source`, por id); el resto se conserva; se
registra un warning con la ficha y los campos retirados.

**Contenido del linaje tras el recálculo**: solo entradas producidas por el motor sobre los miembros vigentes. Los
overrides conservan su atribución (`value_override` → operador; `source_pin` → registro fijado, que es miembro
vigente porque los pins al que salió se desactivaron antes del recálculo). `previous` se rellena como indica Architecture.
El EventLog persistente de DOM-MDM-SURVIVORSHIP-001 §3.6.2 no existe (RFC-ARCH-002): el `previous` del linaje es el
único rastro del valor retirado.

### Error handling

- Todo ocurre en la transacción que cierra el tramo: un fallo revierte también el cierre (nunca "movido pero con
  datos viejos").
- Una excepción del calculador (p. ej. `entity_type` sin schema activo) falla el paso de Persistence y sigue la
  política de reintentos (ADR-013); en unmerge, la petición falla con el mapeo de errores actual.
- Conflicto de bloqueo o de versión sobre `previous` → `OptimisticLockingFailureException` → el orquestador
  re-resuelve la pertenencia y reintenta (DOM-MDM-PIPELINE-001 §6.5 p.5).
- Eventos best-effort tras el commit; un fallo de publicación se registra y no se propaga.

## Acceptance Criteria

- [ ] AC1. Tras un movimiento por ForceRule de un registro enlazado, si la ficha que lo pierde sigue activa, no es
  superviviente protegida y conserva miembros: su `golden_data` es igual y, campo a campo, su `field_lineage` tiene
  los mismos `value`/`source`/`source_record_id`/`rule_applied` que el resultado de `reSurvivorshipFromSources`
  sobre sus miembros vigentes; su `quality_score` difiere del de `/admin/re-survivorship/{id}` en menos de 0.001; y su
  `version` ha subido.
- [ ] AC2. Tras un movimiento por ForceRule o un unmerge, si la ficha que pierde el miembro sigue `active`, ninguna
  entrada de su `field_lineage` tiene la identidad del registro que salió (en `source_record_id` + `source`).
- [ ] AC3. Un movimiento por ForceRule que saca al único miembro deja la ficha con `status = orphaned` (hoy queda
  `active`), `source_count = 0` y sus demás columnas sin cambios; un registro con sus valores no la obtiene como
  candidata.
- [ ] AC4. Un `source_pin` activo de la ficha que pierde el miembro, fijado a ese registro, queda inactivo con
  `deactivation_reason = member_exit` en la misma transacción, y se publica `FieldOverrideAutoDeactivated` tras el
  commit.
- [ ] AC5. Tras el commit se emite `golden_record.updated` para la ficha que pierde el miembro (recalculada u
  orfanada), por ingesta síncrona y asíncrona, y `GoldenRecordQualityChanged` si **su** nota cruza de tier.
- [ ] AC6. Si el recálculo falla, el movimiento no se persiste (tramo, claves y ficha quedan como antes del intento).
- [ ] AC7. Un unmerge cuyos miembros restantes no tienen versión en Silver deja la ficha original sin ningún campo
  atribuido a un registro separado.
- [ ] AC8. Un movimiento por ForceRule concurrente con la re-ingesta de un miembro que se queda en la ficha: ambas
  terminan; ninguna entrada de linaje de la ficha apunta al registro que salió; el campo que solo trae la nueva
  versión del miembro que se queda está en su `golden_data`; su versión subió dos veces.
- [ ] AC9. El test de paridad compara el calculador con `StewardshipService.reSurvivorshipFromSources` **sin
  modificar** (el diff de la rama no toca ese método) sobre fixtures con varias versiones por miembro y una
  `qualityScore` nula; ningún fichero **de producción** nuevo fuera de `mdm-persistence` importa
  `jakarta.persistence` ni repositorios JPA (los tests pueden usarlos, como hoy).
- [ ] AC10. Las ramas `consolidation` y `pipeline_run`/orphan de `persistMembership` no cambian de comportamiento
  (los ITs existentes de `SourceIdentityPipelineIT` y `MultiMatchConsolidationIT` siguen en verde).
- [ ] AC11. Si la ficha que pierde el miembro es la superviviente protegida de un merge manual, solo cambian los
  campos cuya entrada de linaje apuntaba al registro que salió.
- [ ] AC12. Cada campo cuyo valor cambia por el recálculo lleva `previous.value` y `previous.source` con los valores
  anteriores.

## Enmiendas

Gate A2 del plan (2026-09-29), rulings de human:ab-test decididos por el agente con su autorización previa:

- **E1 — Frescura en la retirada de respaldo.** La retirada de respaldo (pipeline y unmerge) calcula
  `latest_source_received_at` con `LatestSourceReceivedAtResolver` sobre las versiones de los miembros que quedan
  (lista vacía → `null`), nunca conserva el valor persistido: DOM-MDM-SURVIVORSHIP-001 §3.7.1.1, "nunca combina el
  valor ya persistido con el candidato nuevo: una operación como `unmerge` puede QUITAR sources, y arrastrar el máximo
  persistido lo dejaría obsoleto". El unmerge recalcula también la nota en esa rama.
- **E2 — `PRODUCED` hacia la ficha que pierde el miembro.** El run que la recalcula u orfana añade `PRODUCED` (run →
  ficha, `action: member_exit`): DOM-MDM-LINEAGE-001 §3.2.5 "Update de golden record | Añade `PRODUCED` (run → GR)".
- **E3 — Cobertura asíncrona.** La ingesta asíncrona pasa por el mismo `PersistenceStepHandler`; su emisión
  post-commit se prueba con un unitario de `AsyncPipelineExecutor` (el E2E asíncrono exige NATS real).
- **E4 — Atribución en entradas de pin legado.** Una entrada de linaje con `rule_applied = source_pin` y `source =
  stewardship` (pin sin `pinned_source`, `DefaultMergeEngine.java:131-136`) cuenta como del registro que salió si su
  `source_record_id` coincide (como una entrada sin `source`).
- **E5 — `previous` solo si cambia.** El aplicador fija `previous` cuando el valor cambia respecto al `golden_data`
  anterior y lo deja `null` en otro caso, aunque el encadenado lo haya rellenado (DOM-MDM-SURVIVORSHIP-001 §3.6.1).
- **E6 — Knowledge gap: contested rule.** DOM-MDM-SURVIVORSHIP-001 §3.2 dice que una ficha `orphaned` no se propaga
  downstream; esta WRK-SPEC emite `golden_record.updated` al orfanarla porque es el único mecanismo de invalidación
  de caché entre pods (ARCH-MDM-PERFORMANCE-001 §3.3.1). La consolidación debe decidir si hace falta un evento
  distinto (`GoldenRecordOrphaned`).
- **E7 — AC8 determinista.** El IT de AC8 intercala de forma determinista: otra transacción bloquea L, añade a Silver
  la versión nueva del miembro que se queda y sube la versión de L, y hace commit cuando el movimiento espera el
  bloqueo; el recálculo debe verla.

```java
import java.util.UUID;

/**
 * Recalcula una ficha desde las versiones en Silver de sus miembros vigentes, con el mismo encadenado create→update
 * que {@code StewardshipService.reSurvivorshipFromSources} (paridad en {@code MemberSurvivorshipParityTest}) y el
 * {@link MergeEngine} inyectado por Spring, para no perder los overrides activos (PROD-MDM-STEWARDSHIP-001 §3.8.5).
 * Calculo puro: no lee ni escribe la ficha.
 *
 * @see <a href="specs/work/WRK-SPEC-MDM-MEMBER-EXIT-001-la-ficha-que-pierde-un-miembro-se-recalcula.md">WRK-SPEC-MDM-MEMBER-EXIT-001</a>
 */
@Component
public class MemberSurvivorshipRecalculator {

    /** Resultado del recalculo completo de una ficha. */
    public record Recomputation(Map<String, Object> goldenData, Map<String, FieldLineageEntry> fieldLineage,
                                QualityScoreResult quality, Instant latestSourceReceivedAt) {}

    private final MergeEngine mergeEngine;
    private final QualityScoreResolver qualityScoreResolver;
    private final LatestSourceReceivedAtResolver latestSourceReceivedAtResolver;

    public MemberSurvivorshipRecalculator(MergeEngine mergeEngine, QualityScoreResolver qualityScoreResolver,
                                          LatestSourceReceivedAtResolver latestSourceReceivedAtResolver) {
        this.mergeEngine = mergeEngine;
        this.qualityScoreResolver = qualityScoreResolver;
        this.latestSourceReceivedAtResolver = latestSourceReceivedAtResolver;
    }

    /**
     * @param versions versiones de los miembros vigentes en el orden de {@code findVersionsOfMembers}
     * @return el recalculo, o {@code null} si no hay versiones
     */
    public Recomputation recompute(List<SourceRecordVersion> versions, SurvivorshipConfig config, String tenantId,
                                   String goldenRecordId, String entityType, Instant evaluationInstant) {
        MergeResult result = survivorship(versions, config, tenantId, goldenRecordId);
        if (result == null) {
            return null;
        }
        Instant latest = latestSourceReceivedAtResolver.resolve(
                versions.stream().map(SourceRecordVersion::receivedAt).toList());
        QualityScoreResult quality = score(tenantId, entityType, result.goldenData(), result.fieldLineage(),
                latest, evaluationInstant);
        return new Recomputation(result.goldenData(), result.fieldLineage(), quality, latest);
    }

    /** Encadenado create→update de {@code StewardshipService.reSurvivorshipFromSources}; {@code null} si vacio. */
    public MergeResult survivorship(List<SourceRecordVersion> versions, SurvivorshipConfig config, String tenantId,
                                    String goldenRecordId) {
        if (versions.isEmpty()) {
            return null;
        }
        MergeResult result = null;
        for (SourceRecordVersion v : versions) {
            MergeRequest req = new MergeRequest(
                    result == null ? "create" : "update", v.normalizedData(),
                    result == null ? null : result.goldenData(), result == null ? null : result.fieldLineage(),
                    config, v.identity().source(), v.identity().sourceRecordId(),
                    1.0, v.qualityScore() != null ? v.qualityScore().doubleValue() : 0.8,
                    "re-survivorship-" + UUID.randomUUID(), goldenRecordId, tenantId,
                    null, null, null);
            result = mergeEngine.merge(req);
        }
        return result;
    }

    /** Nota de la ficha con el resolver compartido (ADR-014, dueno unico). */
    public QualityScoreResult score(String tenantId, String entityType, Map<String, Object> goldenData,
                                    Map<String, FieldLineageEntry> fieldLineage, Instant latestSourceReceivedAt,
                                    Instant evaluationInstant) {
        return qualityScoreResolver.resolve(new QualityScoreInput(tenantId, entityType, goldenData, fieldLineage,
                latestSourceReceivedAt, evaluationInstant));
    }
}
```

```java
package com.mdm.ingest.survivorship;

import com.mdm.core.domain.merge.FieldLineageEntry;
import com.mdm.core.domain.merge.FieldLineageEntry.FieldLineagePrevious;
import com.mdm.core.domain.membership.SourceRecordIdentity;

import java.time.Instant;
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.LinkedHashSet;
import java.util.List;
import java.util.Map;
import java.util.Objects;
import java.util.Set;

/**
 * Lo que queda en la ficha que pierde miembros (WRK-SPEC-MDM-MEMBER-EXIT-001 §Data flow): recalculo completo,
 * parcial (superviviente protegida de un merge manual, PROD-MDM-STEWARDSHIP-001 §3.8.5) o retirada de respaldo. Los
 * campos que cambian llevan {@code previous} con el valor y la fuente anteriores (DOM-MDM-SURVIVORSHIP-001 §3.6.1).
 */
public final class MemberExitApplier {

    /** @param changedFields campos cuyo valor cambio o desaparecio */
    public record Applied(Map<String, Object> goldenData, Map<String, FieldLineageEntry> fieldLineage,
                          List<String> changedFields) {}

    private MemberExitApplier() {}

    public static Applied full(Map<String, Object> before, Map<String, FieldLineageEntry> beforeLineage,
                               Map<String, Object> recomputedData,
                               Map<String, FieldLineageEntry> recomputedLineage, Instant now) {
        Map<String, Object> data = new LinkedHashMap<>(recomputedData);
        Map<String, FieldLineageEntry> lineage = new LinkedHashMap<>();
        recomputedLineage.forEach((f, e) -> lineage.put(f, withPrevious(f, e, before, beforeLineage, now)));
        return new Applied(data, lineage, changed(before, data));
    }

    public static Applied partial(Map<String, Object> before, Map<String, FieldLineageEntry> beforeLineage,
                                  Map<String, Object> recomputedData,
                                  Map<String, FieldLineageEntry> recomputedLineage,
                                  List<SourceRecordIdentity> departed, Instant now) {
        Map<String, Object> data = new LinkedHashMap<>(before);
        Map<String, FieldLineageEntry> lineage = new LinkedHashMap<>(beforeLineage);
        beforeLineage.forEach((f, e) -> {
            if (!pointsTo(e, departed)) {
                return;
            }
            if (recomputedData.containsKey(f)) {
                data.put(f, recomputedData.get(f));
                lineage.put(f, withPrevious(f, recomputedLineage.get(f), before, beforeLineage, now));
            } else {
                data.remove(f);
                lineage.remove(f);
            }
        });
        return new Applied(data, lineage, changed(before, data));
    }

    public static Applied strip(Map<String, Object> before, Map<String, FieldLineageEntry> beforeLineage,
                                List<SourceRecordIdentity> departed) {
        Map<String, Object> data = new LinkedHashMap<>(before);
        Map<String, FieldLineageEntry> lineage = new LinkedHashMap<>(beforeLineage);
        beforeLineage.forEach((f, e) -> {
            if (pointsTo(e, departed)) {
                data.remove(f);
                lineage.remove(f);
            }
        });
        return new Applied(data, lineage, changed(before, data));
    }

    /**
     * La entrada atribuye el campo a uno de {@code departed}. Casan solo por id: una entrada legada sin
     * {@code source} y la de un pin legado ({@code rule_applied = source_pin}, {@code source = stewardship},
     * {@code DefaultMergeEngine.java:131-136}); el resto, por identidad completa (WRK-SPEC E4).
     */
    public static boolean pointsTo(FieldLineageEntry entry, List<SourceRecordIdentity> departed) {
        if (entry == null || entry.sourceRecordId() == null) {
            return false;
        }
        boolean byIdOnly = entry.source() == null
                || ("source_pin".equals(entry.ruleApplied()) && "stewardship".equals(entry.source()));
        return departed.stream().anyMatch(d -> d.sourceRecordId().equals(entry.sourceRecordId())
                && (byIdOnly || d.source().equals(entry.source())));
    }

    /**
     * {@code previous} solo si el valor cambia respecto al golden_data anterior; si no (o si el campo es nuevo),
     * {@code null}, aunque el encadenado create→update lo haya rellenado (WRK-SPEC E5; §3.6.1).
     */
    private static FieldLineageEntry withPrevious(String field, FieldLineageEntry e, Map<String, Object> before,
                                                  Map<String, FieldLineageEntry> beforeLineage, Instant now) {
        if (e == null) {
            return null;
        }
        FieldLineagePrevious previous = null;
        if (before.containsKey(field) && !Objects.equals(before.get(field), e.value())) {
            FieldLineageEntry old = beforeLineage.get(field);
            previous = FieldLineagePrevious.of(before.get(field), old != null ? old.source() : null, now);
        }
        return new FieldLineageEntry(e.value(), e.source(), e.sourceRecordId(), e.ruleApplied(), e.resolvedAt(),
                e.confidence(), e.conflict(), e.competingValues(), previous);
    }

    private static List<String> changed(Map<String, Object> before, Map<String, Object> after) {
        Set<String> fields = new LinkedHashSet<>(before.keySet());
        fields.addAll(after.keySet());
        List<String> changed = new ArrayList<>();
        for (String f : fields) {
            if (!Objects.equals(before.get(f), after.get(f))) {
                changed.add(f);
            }
        }
        return changed;
    }
}
```

```java
    /** Motivo de desactivacion de un source_pin cuyo registro salio de la ficha (WRK-SPEC-MDM-MEMBER-EXIT-001). */
    public static final String MEMBER_EXIT_REASON = "member_exit";

    /**
     * DOM-MDM-PIPELINE-001 §10.9.4 p.2: desactiva los {@code source_pin} activos de la ficha fijados al registro que
     * acaba de salir de ella (identidad completa; un pin legado sin {@code pinnedSource} casa por id). Escribe en la
     * transaccion de Persistence; {@code FieldOverrideAutoDeactivated} se publica tras el commit.
     *
     * @return numero de pins desactivados
     */
    public int deactivatePinsTo(String goldenRecordId, SourceRecordIdentity departed, PipelineContext ctx,
                                Instant now) {
        String tenant = ctx.getTenantId();
        int deactivated = 0;
        for (FieldOverrideRuleEntity pin : repository.findByGoldenRecordIdAndTenantIdAndActiveAndOverrideType(
                UUID.fromString(goldenRecordId), tenant, true, OverrideType.SOURCE_PIN.name())) {
            String pinned = pin.getPinnedSourceRecordId();
            if (pinned == null || !pinned.equals(departed.sourceRecordId())
                    || (pin.getPinnedSource() != null && !pin.getPinnedSource().equals(departed.source()))) {
                continue;
            }
            pin.setActive(false);
            pin.setDeactivatedAt(now);
            pin.setDeactivatedBy(DEACTIVATED_BY);
            pin.setDeactivationReason(MEMBER_EXIT_REASON);
            repository.saveAndFlush(pin);
            deactivated++;
            String field = pin.getField();
            String type = pin.getOverrideType();
            afterCommit(() -> eventEmitter.emitFieldOverrideAutoDeactivated(goldenRecordId, ctx.getEntityType(),
                    field, type, MEMBER_EXIT_REASON, null, pinned, ctx.getPipelineRunId(), ctx.getSource(), tenant));
        }
        if (deactivated > 0) {
            log.info("Member exit {} from {}: source pins deactivated={}", departed.display(), goldenRecordId, deactivated);
        }
        return deactivated;
    }
```

# WRK-TASK-MDM-MEMBER-EXIT-001-005 — La ficha que pierde un miembro, en Persistence

## Objective

Conectar 002–004 en `PersistenceStepHandler.persistMembership`: tras mover por ForceRule un registro fuera de una
ficha activa, en la misma transacción y con la ficha bloqueada, desactivar sus pins al registro, recalcularla
(completo; parcial si es superviviente protegida; retirada si no hay versiones) o pasarla a `orphaned` si no le quedan
miembros, y apuntarla en el contexto para el evento post-commit (006).

```java
    private static final TypeReference<Map<String, Object>> DATA_TYPE = new TypeReference<>() {};

    /**
     * Regla de la ficha que pierde un miembro (WRK-SPEC-MDM-MEMBER-EXIT-001 §Data flow; DOM-MDM-PIPELINE-001
     * §10.8.4 p.3): tras mover {@code departed} fuera de {@code previous} (ya bloqueada), si sigue activa desactiva
     * sus pins al registro que salio (§10.9.4 p.2) y, con miembros vigentes, la recalcula — parcial si es la
     * superviviente de un merge manual (PROD-MDM-STEWARDSHIP-001 §3.8.5), retirada de respaldo sin versiones en
     * Silver —; sin miembros pasa a {@code orphaned} (DOM-MDM-SURVIVORSHIP-001 §3.2). Misma transaccion que el
     * movimiento (§6.5 Atomicidad): un fallo lo revierte todo.
     */
    private void applyMemberExit(PipelineContext ctx, String previous, SourceRecordIdentity departed) {
        if (memberRecalculator == null || versionReader == null) {
            return;
        }
        GoldenRecordEntity gr = goldenRecordRepository.findById(UUID.fromString(previous)).orElse(null);
        if (gr == null || !GoldenRecordStatus.ACTIVE.getValue().equalsIgnoreCase(gr.getStatus())) {
            return;
        }
        Instant now = Instant.now();
        if (overrideMigrator != null) {
            overrideMigrator.deactivatePinsTo(previous, departed, ctx, now);
        }
        ctx.addMemberExitGoldenRecordId(previous);
        List<SourceRecordIdentity> members = membershipRepository.findCurrentMembers(ctx.getTenantId(), previous)
                .stream().map(MembershipSpan::identity).toList();
        gr.setUpdatedAt(now);
        gr.setUpdatedBy(ctx.getUserId());
        if (members.isEmpty()) {
            gr.setStatusEnum(GoldenRecordStatus.ORPHANED); // el resto de columnas queda como historia
            goldenRecordRepository.saveAndFlush(gr);
            addMemberExitProducedEdge(ctx, previous);
            log.info("Golden record {} lost its last member {}: orphaned", previous, departed.display());
            return;
        }
        Map<String, Object> before = gr.getGoldenData() != null
                ? objectMapper.convertValue(gr.getGoldenData(), DATA_TYPE) : Map.of();
        Map<String, FieldLineageEntry> beforeLineage = readFieldLineage(gr.getFieldLineage());
        MemberSurvivorshipRecalculator.Recomputation r = memberRecalculator.recompute(
                versionReader.findVersionsOfMembers(ctx.getTenantId(), ctx.getEntityType(), members),
                ctx.getSurvivorshipConfig(), ctx.getTenantId(), previous, ctx.getEntityType(), now);
        boolean protectedSurvivor = forceRuleRepository != null
                && !forceRuleRepository.findActiveGoldenToGoldenTargets(ctx.getTenantId(), List.of(gr.getId())).isEmpty();
        MemberExitApplier.Applied applied;
        Instant latest;
        QualityScoreResult quality;
        if (r == null) {
            applied = MemberExitApplier.strip(before, beforeLineage, List.of(departed));
            latest = null; // E1: frescura sobre los que quedan, sin versiones → null (§3.7.1.1)
            quality = memberRecalculator.score(ctx.getTenantId(), ctx.getEntityType(), applied.goldenData(),
                    applied.fieldLineage(), latest, now);
            log.warn("Golden record {} lost {} and its members have no Silver version: withdrew {}",
                    previous, departed.display(), applied.changedFields());
        } else if (protectedSurvivor) {
            applied = MemberExitApplier.partial(before, beforeLineage, r.goldenData(), r.fieldLineage(),
                    List.of(departed), now);
            latest = r.latestSourceReceivedAt();
            quality = memberRecalculator.score(ctx.getTenantId(), ctx.getEntityType(), applied.goldenData(),
                    applied.fieldLineage(), latest, now);
        } else {
            applied = MemberExitApplier.full(before, beforeLineage, r.goldenData(), r.fieldLineage(), now);
            latest = r.latestSourceReceivedAt();
            quality = r.quality();
        }
        BigDecimal previousScore = gr.getQualityScore();
        gr.setGoldenData(objectMapper.valueToTree(applied.goldenData()));
        gr.setFieldLineage(objectMapper.valueToTree(applied.fieldLineage()));
        gr.setQualityScore(BigDecimal.valueOf(quality.score()));
        gr.setLatestSourceReceivedAt(latest);
        goldenRecordRepository.saveAndFlush(gr);
        maybeEmitQualityTierChange(previousScore, gr, ctx, quality);
        addMemberExitProducedEdge(ctx, previous);
    }

    /** E2: DOM-MDM-LINEAGE-001 §3.2.5 "Update de golden record | Añade PRODUCED (run → GR)". */
    private void addMemberExitProducedEdge(PipelineContext ctx, String goldenRecordId) {
        if (graphStore == null) {
            return;
        }
        graphStore.addEdge(new LineageEdge(null, "PipelineRun", ctx.getPipelineRunId(), "GoldenRecord",
                goldenRecordId, LineageEdgeType.PRODUCED, ctx.getTenantId(), Instant.now(),
                Map.of("action", "member_exit")));
    }

    /** field_lineage campo a campo; una entrada ilegible se descarta (mismo criterio que stewardship). */
    private Map<String, FieldLineageEntry> readFieldLineage(JsonNode node) {
        Map<String, FieldLineageEntry> out = new LinkedHashMap<>();
        if (node == null) {
            return out;
        }
        node.fields().forEachRemaining(e -> {
            try {
                out.put(e.getKey(), objectMapper.convertValue(e.getValue(), FieldLineageEntry.class));
            } catch (IllegalArgumentException ex) {
                log.warn("Unreadable field_lineage entry {}: {}", e.getKey(), ex.getMessage());
            }
        });
        return out;
    }
```

# WRK-TASK-MDM-MEMBER-EXIT-001-006 — Evento post-commit de la ficha que pierde un miembro

## Objective

Hoy los dos emisores post-commit del pipeline solo publican eventos de `context.getGoldenRecordId()` (el destino).
La ficha que pierde el miembro (recalculada u orfanada en 005) debe publicar `golden_record.updated`: es el evento
canónico que consume `CacheInvalidationListener` en los demás pods (ARCH-MDM-PERFORMANCE-001 §3.3.1) y, para una
ficha recalculada, el que avisa downstream de su cambio (DOM-MDM-SURVIVORSHIP-001 §3.8.2 d). Para una ficha
`orphaned` se emite el mismo evento solo como invalidación de caché: §3.2 dice que una `orphaned` no se propaga, y la
WRK-SPEC lo registra como *contested rule* (E6).

```java
        long ms = persistence.get("duration_ms").asLong();

        assertThat(fieldsPointingTo(lineage(l), "erp_sap", "X2")).isEmpty();
    }
```
